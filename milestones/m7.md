# M7 — Settings, flow, and the graded bank

Breakdown of M7 from `implementation_plan.md` §5 (plan estimate 10–16 hours; the sub-goals below add to roughly 12–14 build hours plus content hours on the treadmill's clock).

M6 closed on 2026-09-07 with the game looking like one thing: a pixel theme, a reveal that teaches, a board whose legal moves lift toward the mouse. What it still lacks is everything a *player* asks for after the second game: a way back through the wizard, a way to pause, a way to sit with a wrong answer for as long as it takes to read the right one, and a way to make the game harder or easier than the one setting it ships with. M7 is that list, plus the content work that makes "harder" mean something — every question graded, and the grade finally read by code.

**Order of work: the mechanism before its screen, again.** M6 learned that restyling before the mechanics land means restyling twice; M7's version is that a Settings *screen* built before settings *ride into the game* is a screen with nothing behind it. So board size and move limit become config first, proven by tests and a hand-edited default, and the screen that edits them comes second. The pause screen and the back buttons are the same shape: small state-machine changes with a thin visual on top. Content runs alongside and gates only the last engineering step.

**Budget, honestly.** Three new screens (Settings, Pause, and the popup's Continue variant) each need the pixel theme's treatment, but every one of them is built from the primitives M6.f already has — panel, button, text, and one new widget for choosing among options. If a sub-goal needs a new *kind* of drawing, that's the signal to stop and ask why. The 30-hour gate was passed at M6; M7 is portfolio polish and student value, measured the same way but no longer racing anything.

## Decisions made

- **Settings ride in the config, not in constants** *(plan §5, 2026-09-06)*. `GameConfig` grows a nested, frozen `Settings` value (board size, move limit, difficulty policy) that the menus assemble and `PlayState` reads. `MOVE_LIMIT` and `Board(5, 5)` in `constants.py`/`play.py` become *defaults* the settings start from, never a second source of truth. Replays keep the settings because replay rebuilds `PlayState` from the same config; Main Menu resets nothing but the state machine — the settings live on `Game` for the session.
- **Presets write into the controls; custom leaves them editable** *(David, 2026-09-06)*. The Settings screen's top control is **Difficulty — easy / medium / hard / custom**. Choosing a preset stamps values into the controls beneath it (board size, move limit, question tier policy); *custom* is what the screen becomes the moment a control is edited by hand. There is no fourth hidden state: the preset control shows *custom* whenever the values don't match a preset, and the mapping preset → values is a small table in `game_setup.py`, tested.
- **Board size is the first difficulty lever, move limit the second, question tier the third** *(§7, reaffirmed)*. Board size 5×5 / 7×7 / 9×9 scales herding distance with no other code change — the fixed-region/derived-cell-size design finally earning its keep. The move limit scales with it: 15 was tuned for a start distance of 4 on 5×5 (M6.e, 2026-09-07); 7×7 starts at distance 6 and 9×9 at 8, and the early-loss rule (moves < distance → lose) makes an untuned limit a fast loss. Starting points offered 2026-09-07 were easy 5×5/20/tier 1, medium 5×5/15/all, hard 7×7/~22/distance. **David's table, shipped 2026-09-08 in M7.a:** **easy** 5×5 / 15 / tiers 1+2; **medium** 7×7 / 20 / all tiers; **hard** 9×9 / 25 / distance-scaled. Easy is the default preset, so the shipped board and move limit are M6's; the tier policy differs from M6's implicit "all" and starts to matter only when M7.f reads it. The numbers stay playtest knobs.
- **Pause is a sixth state that draws the play state beneath it** *(plan §5)*. A button top-right during play opens a panel with **Main Menu / Continue / Retry**. Retry is exactly Play Again (same config, fresh scramble, the same living bank). The pause state's `update` does *not* forward `dt` to the play state, which is what freezes the reveal timer and the tile tweens for free — the first time a non-play `update` has a job, and it's a no-op on purpose.
- **Back buttons go in the wizard; the game itself has no back** *(m4.md's deferral coming due)*. Subject → Game Select, Topics → Subject, Settings → Game Select. Back keeps whatever was chosen on the screen being left (a Topics selection survives a trip back to Subject and forward again) because the states are rebuilt from `Game`-held values, not from scratch.
- **Click-to-continue on wrong answers only** *(David, 2026-09-06; the extra second from M6.e was the stopgap)*. A wrong answer holds the reveal — chosen button faded, correct one lit — until the student clicks **Continue**. Correct answers keep the short timed reveal (1300 ms), because there's nothing to read. `WRONG_REVEAL_EXTRA_MS` retires when this ships.
- **Grading is content and comes first; wiring reads it second** *(§7 rule, unchanged)*. Every question gets a 1–3 grade per the M5 rubric (1 recall, 2 application, 3 analysis), on the treadmill's clock, informed by the playtest notes on which questions bite. M7.f, the code that filters by tier, does not start until the bank is graded — and it must degrade gracefully anyway, because a pool with no question at the wanted tier is a fact of content, not a bug.
- **Small pools cycle off the board instead of recycling in place** *(David, 2026-09-09; shipped in the M7.a–d tree)*. Some subtopics hold only 1–3 questions, and a student who lands on the same square a few times would otherwise learn the answers rather than the anatomy. So when a (topic, subtopic) pool has no unused question left, the cells carrying it are relabeled to pools that still do; a pool recycles only when *every* selected pool is dry, at which point all of them restart. The bank's no-repeat contract is unchanged — this is a rule about which pairs the board shows, layered over it (`available_pools`, `restart_pools`, `next_unused_question` in `questions.py`; `_refresh_exhausted_cell_topics` in `play.py`). *Resolved 2026-09-09 (David): the all-dry restart now returns before relabeling, so the board is preserved; a dry pool's cells go to the live pool with the fewest cells on the board (a `Counter`, ties broken by the injected rng), so balance holds. Tests in `tests/test_pool_cycling.py` (Claude): bank rules, the label-matches-question contract over ten asks, balance after a cycle, the restart keeping every label, seeding, and a replay on a living bank hiding dry pools before the first click.*

- **Sprites are last** *(moved from M6.f.4, 2026-09-07 — waiting on David's artist)*. The spec lives in `milestones/m6.md` M6.f.4; nothing else in M7 depends on it.
- **Out of scope, still:** Red and both Run-from-Red modes, fill-in-the-blank input, sound, packaging, keyboard navigation of menus (an Esc-to-pause hotkey is a one-line stretch, not a goal), and any settings persistence to disk — settings live for the session and reset on relaunch.

**One design question for David, from the review — the deferred button press.** Every button now plays a press animation (`ButtonAction`, 60 ms down + 40 ms hold) and fires its action *after* it, discarding all input meanwhile and the batch after. The catch: the delay exists only where the theme's lift is nonzero, so on pixel a click lands ~100 ms later and swallows one extra batch, while on flat it lands immediately — the same click sequence produces different state-machine timing per theme, which breaks M6's rule that a theme is data and never behavior, and it's why 24 tests and the gallery had to learn to "settle" after every press. Options, cheapest first: (a) fire the callback on the click and let the press animation be purely cosmetic ("the model moves instantly, the view catches up" — the game's own rule); (b) keep the delay but make it theme-independent and injectable to zero for tests, the way `reveal_duration_ms` is. The tests as written pass under either.

*Resolved 2026-09-08 (Claude, at David's request): option (b) without the injection. The early-return in `ButtonAction.begin` that fired the callback immediately when the theme's lift was zero is gone, so every theme locks input for `BUTTON_PRESS_DOWN_MS + BUTTON_PRESS_HOLD_MS` before the action lands. Firing on the click was rejected because five of the seven uses change state, which would leave the press animation invisible exactly where it was wanted. Flat now has a 100 ms wait with no visible motion; a darker "pressed" face for flat would be a renderer style if it ever bothers anyone. ## Traps

1. **Two truths for a setting.** `MOVE_LIMIT` in `constants.py` *and* `settings.move_limit` in the config is how a 7×7 game ends up with a 5×5 move limit. After M7.a the constant is the default that seeds the settings and nothing reads it at play time.
2. **A preset stored next to its values.** If the screen stores `preset = "hard"` and the values separately, they drift the first time a row is edited. Derive the preset name from the values every time; store only the values.
3. **The pause state forwarding `dt`.** One helpful-looking `self.play_state.update(dt_ms)` in `PauseState.update` and the reveal expires behind the pause panel, Blue flees unseen, and the tiles keep tweening under a frozen screen. Forward nothing.
4. **Continue's click discarded by the reveal's own rule.** M6.c discards the event batch on the expiry frame. If the click-to-continue exit reuses that rule blindly, the Continue click is discarded by the frame it arrives in and nothing ever resolves. Resolve on the click, then discard the rest.
5. **Tier filtering that breaks the rotation contract.** A per-tier used-set or a per-tier shuffled order silently reintroduces repeats across tiers. One pool order, one used-set; the tier is a filter over the walk, never a second pool.
6. **Building M7.f on the ungraded bank.** With every question at 1, `"tier1"` is `"all"` and `"distance"` is `"all"` with extra steps — the tests would pass and prove nothing. Grade first; the seeded tests use a synthetic bank with all three tiers.
7. **Labels overflowing on 9×9.** The M6.f.1 measurement was for 128 px cells; 88 px cells at the pixel label size will overflow dozens of labels. Run `tools/theme_fit.py` at each board size before the size toggle ships, and expect the label font size to become per-board-size theme data.
8. **The early-loss rule on a bigger board.** Start distance 8 on 9×9 with a 15-move limit is a loss after two wrong answers. The move limit *must* scale with the board; the presets table is where that relationship lives, and the M7.a success check is where it's felt.
9. **A new widget that draws.** The option row must go through `render.button`; the AST guard test will fail the moment `ui.py` calls `pygame.draw` directly, and that's the guard doing its job. A selected look is a theme style, not a new primitive.
10. **Settings that survive a relaunch by accident.** Nothing persists to disk in M7. If a test or a driver sets `Game.settings` and a later test sees it, that's shared state between tests, not a feature.
11. **The back button rebuilding state from nothing.** Back that drops the Topics selection is worse than no Back. Either keep the state object and re-enter it, or rebuild from `Game`-held values; both are fine, forgetting is not.
