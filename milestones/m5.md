# M5 — Content: the bank becomes real

Breakdown of M5 from `implementation_plan.md` §5 (est. 10–16 hours, most of it authoring — see the gate-accounting note in §5: content hours are coursework, not engineering).

M0–M4 built a machine; M5 gives it something to teach. The honest inventory as of 2026-08-31: all 81 prompts are placeholders ("Question1"…), every difficulty is 1, and 30 questions sit under literal "Filler N" subtopics. Nothing about the *game* changes in this milestone — what changes is that playing it starts being worth something.

The milestone has a small engineering half and a large content half, and the engineering half goes **first**, because every piece of it exists to make the content half safer or more pleasant: load-time guards that catch authoring mistakes at startup instead of mid-game, the `subject` field landing before 200 questions are born without it, a per-topic file split so authoring diffs stay small, a Topics screen that survives the topic list growing, and a runtime answer shuffle that lands *before* the import so no question is ever hand-scrambled.

## Decisions made

- **Deep bank, deliberately** *(decided 2026-08-31)*. 8+ questions per subtopic, 200+ total. This knowingly overrides the plan's trap 4 ("20–30 questions is plenty to prove the game works") — because proving the game works stopped being the goal in M4. The game works. Now it's a study resource for the A&P students David tutors, which makes question quality the product. The 30-hour gate is measured against build hours only (recorded in §5).
- **David curates everything; open banks feed the curation** *(revised 2026-08-31 — David tutors A&P; question quality for his students outranks writing-from-scratch)*. Questions come from his teaching materials (Martini, *Fundamentals of Anatomy & Physiology* 12e) and from **openly licensed** question banks — selected, fact-checked, and adapted by David, who remains the editor of every card. Only open-licensed sources may be copied or adapted into the data files (CC BY / CC BY-SA / CC BY-NC-SA — never pirated publisher test banks); `data/questions/ATTRIBUTION.md` records each source and its license, which satisfies the attribution condition every CC license carries and settles "where did this question come from" forever. Free-but-copyrighted quiz sites may inspire, never be copied. Candidate open banks, with licenses and caveats, are listed in `question_sources.md` at the repo root.
- **Content lands incrementally; the commit doesn't wait for 200.** The game runs fine on a partial bank — thin pools recycle, that's what the recycle policy is for. M5 is *done* at a baseline (below); the climb from baseline to 8+ per subtopic continues on its own clock through M6 and beyond.
- **Difficulty is tagged now, consumed later** *(decided 2026-08-31)*. Every question written in M5 gets a meaningful 1–3 tag — **1 = recall** (define, identify), **2 = application** (use it on a scenario), **3 = analysis** (multi-step, compare, predict). No difficulty UI ships in M5; the tags wait for the §7 difficulty-presets knob. Tagging while writing costs seconds per question; re-tagging 200 later is the bad timeline.
- **One file per topic** *(decided 2026-08-31)*. `anatomy_physiology.json` splits into `anatomical_language.json`, `cells.json`, `chemical_foundations.json`, `tissues.json`. M3's decision holds — files are authoring containers, the `topic` field stays the only truth, and the loader already globs the directory — so the split changes nothing but ergonomics: smaller files, smaller diffs, less scrolling mid-authoring.
- **The subject layer is a field, settled early** *(decided 2026-08-31, flipping the §7 deferral ahead of schedule)*. Every question carries `subject` — the M3 topic-from-data principle extended a level up, completing the in-data hierarchy **subject → topic → subtopic**. `QuestionBank` grows the matching top rung of the ladder — `subjects` and `topics(subject)`, each the same filtered-sorted-set computation as the two rungs below — and `TopicsState` starts consuming `topics(config.subject)`, so the Subject screen's choice becomes real plumbing even while only one subject exists. The alternatives lost on drift: a hand-kept subject→topics dict is a second copy of the truth whose failure mode is an invisibly unlisted topic (the registry pattern this project has now declined four times), and subject-as-directory makes *location* meaningful — a misfiled file mislabels every question inside, with nothing in the file for a guard to check against. Settled now, before the treadmill, so all 200+ real questions are born with the field instead of retrofitted. The Subject *screen* keeps its hardcoded two buttons through M5 (deriving from `bank.subjects` would drop the aspirational "Organic Chemistry (coming soon)" tease); it switches to data-derived buttons when a second subject's content actually lands.
- **Two refinements keep the losing options' conveniences without their costs** *(decided 2026-08-31)*. Subject *folders* are welcome as shelves: `data/questions/anatomy_physiology/cells.json` is fine whenever it feels tidier, because the loader rglobs everything and the folder never decides anything — nominal, not functional; the field alone is truth. And the menu layer keeps a small *display-name* dict (`anatomy_physiology` → "Anatomy & Physiology") with `prettify_topic` as the fallback, since `title()` can't invent an ampersand — allowed precisely because it's cosmetic-only: a drifted display entry costs a label, never reachability. The dividing line, stated once for all future cases: **identity is never hand-maintained; labels may be.**
- **Harden the loader before the treadmill** *(decided 2026-08-31)*. Three load-time guards, each aimed at a mistake that 200 hand-typed questions will eventually make:
  1. **Syntax errors get a filename.** The §7 knob, flipped on schedule: wrap `json.load` in the same catch-enrich-reraise the loader already applies around `from_dict`, so a stray comma reports the file, not just "line 3 column 5" of nowhere.
  2. **Duplicate ids are rejected.** Rotation keys used-marks on `id`; a copy-pasted question block with an unedited id silently corrupts rotation for *both* questions. The bank refuses to load them.
  3. **Near-identical subtopics are rejected.** m3.md trap 9 arriving on schedule: two subtopics in the same topic that differ only by case or surrounding/extra whitespace ("Body Regions" vs "body  regions") are one typo'd pool split in two — refuse at load, naming both spellings.
- **Answers shuffle at display time; the files stay canonical** *(decided 2026-09-01)*. Choice order is randomized by the game each time a question is asked, never by hand in the JSON. Hand-scrambling lost on three counts: every manual reorder must keep `answer_index` in sync, and the loader can only catch an out-of-bounds index — a wrong-but-valid one silently marks the wrong answer correct, the worst bug a study tool can have; a stored order is frozen, so a recycled question teaches "it was B" instead of the anatomy; and an unscrambled file is auditable at a glance. The shuffle is a *presentation* concern: `Question` stays immutable and the play state owns a per-ask display order — the same model/view split the board already lives by. Randomness comes from the injected `Random` that `assign_cell_topics` already draws from; module-level `random` stays out, so tests stay seedable. Questions whose choices are positional ("all of the above") opt out with `"shuffle": false` in the data; the field is optional and absent means shuffle. New questions may be written answer-first (`answer_index: 0`) since players never see stored order — and existing files need no migration, because the shuffle works with any valid index.
- **Cells and tissues get their real sections before their questions.** Subtopic names are pool identities — renaming one mid-treadmill invalidates nothing in code but everything in your mental map of what's written. Settle the section list for each topic first, then write into it.

| File | Owns |
|---|---|
| `data/questions/*.json` | one file per topic (subject folders optional, as shelves); real prompts, real sections, `subject` on every question, difficulty tagged 1–3 |
| `questions.py` | the three new load-time guards (syntax filename, duplicate ids, near-collisions); `subject` in `Question`/`from_dict`; `subjects` and `topics(subject)`; the optional `shuffle` flag |
| `states/menus.py` | the Topics screen's scrollable checkbox region, stationary Start; topics listed via `topics(config.subject)`; the subject display-name dict |
| `states/play.py` | the per-ask shuffled display order; clicks resolved to canonical indices before `is_correct` |
| `tests/test_questions.py` | grows a case per new guard, plus the subject rungs of the ladder, plus the shuffle properties (permutation, answer tracking, opt-out, determinism) |

### M5.d — The Topics screen scrolls (~90 min)

- [x] The checkbox list lives in a scroll region: mouse wheel moves it, the title and Start button hold still
- [x] Scrolling clamps — no scrolling past the first or last checkbox
- [x] Clicks hit what the eye sees: hit-testing accounts for the scroll offset (trap 1 below)
- [x] Checkboxes outside the region don't draw over the title or Start (clipping)

**Success check:** temporarily triple the topic list (fake entries in a scratch JSON), scroll through it, click boxes at the top, middle, and bottom of the region — every click lands on the box under the cursor, and nothing bleeds outside the region. Delete the fakes after.

pygame gives you `pygame.MOUSEWHEEL` events (`event.y` is ±1 per notch) and `Surface.set_clip` for the region — between those and an integer offset, no new widget class is required until proven otherwise. The offset is *one* number owned by the Topics state; both drawing and hit-testing must consult it, which is the whole trap.

### M5.e — Answers shuffle at display time (~60–90 min)

- [x] Each ask shows the choices in a fresh shuffled order; the `Question` object and the bank's data never change, so a recycled question reshuffles
- [x] One index convention, applied in both directions: either the display slot the player clicks resolves back to a canonical index before `is_correct`, or the state carries the correct *display* slot and compares those — pick one, never mix (trap 10)
- [x] `"shuffle": false` on a question preserves authored order; absent means shuffle
- [x] The shuffle draws from the injected `Random`, not module-level `random`
- [x] Tests: a shuffled view is a permutation of the question's choices; across many seeded shuffles the tracked correct slot always holds the correct answer's text; a `shuffle: false` question comes back in file order; the same seed produces the same order

*Verified 2026-09-01 (Claude): full suite 134 passing; plus a headless synthetic-click run over 20 seeds — correct answers clicked at their shuffled positions always moved the player with Blue holding, wrong answers always held the player with Blue fleeing, 16/20 first asks showed non-identity orders.*

**Success check:** in the REPL with a seeded `Random`, take one question's shuffled view a handful of times — every view holds the same choices, the tracked slot always reads the right answer, and a `shuffle: false` question never moves. Then in the game, answer a question correctly by its *new* position and watch the catch/move resolve as correct — proof the click landed canonically.

Two shapes both satisfy the checkboxes, and the pick is yours. Either the play state builds a display order when it asks — a shuffled list of canonical indices, stored alongside `pending`; `build_question_popup` builds buttons from it instead of iterating `question.choices` directly, and the click loop maps the clicked slot through it before calling `is_correct` — or `Question` grows a small method taking an rng and returning the shuffled choices plus the correct display slot, and the state compares slots. The first keeps `Question` pure data; the second keeps answer knowledge next to `is_correct` where it already lives. Whichever you choose, notice that `PlayState` *receives* `rng` today but only `__init__` uses it, then lets it go — an ask-time shuffle needs it at ask time, which tells you where it now has to live. Do this before the treadmill: the whole point is that no imported question is ever hand-scrambled and no stored order is ever load-bearing.

## Traps

1. **Scroll offset splits the truth in two.** The checkbox draws at `y - offset` but its rect still says `y` — click-through ghosts, the classic scroll bug. Pick one convention: either mutate/derive the drawn rects from the offset and hit-test those, or keep rects fixed and transform the mouse point by the offset before testing. Either works; mixing them is the bug.
2. **Clipping is opt-in.** Without `set_clip` (or equivalent), a scrolled list happily draws over the title above it and the Start button below it. Set the clip for the list, draw, then *reset* it — a forgotten reset clips everything drawn after.
3. **`MOUSEWHEEL` has a sign convention.** `event.y > 0` is scroll-up on most setups but it's worth ten seconds of print-and-check rather than shipping inverted scrolling.
4. **Duplicate ids fail silently without the guard.** Two questions sharing an id share a used-mark: ask one, both count as used; recycle one pool, resurrect both. That's why M5.a rejects them at load rather than trusting 200 hand-typed ids.
5. **JSON is stricter than your fingers.** Trailing commas, single quotes, a lost `]` — at authoring volume these are *when*, not *if*. After M5.a they cost seconds; without it they cost a stack trace with no filename.
6. **Renaming a subtopic mid-treadmill.** Nothing in code breaks — pools are just strings — but every question already written under the old name silently becomes a separate pool from the ones written under the new. Settle section names first (M5.c), then treat them as frozen identifiers, same as `topic`.
7. **Content in tests.** The temptation grows with the bank: "assert the cells topic has 40 questions" breaks on every authoring commit. The smoke test asserts *shape* (loads, validates, every topic has subtopics) and nothing else — M3.f's "content is data, not behavior" rule, now under real pressure.
8. **Non-ASCII is coming.** °C, µm, H₂O, α-helix. Every `open` already says `encoding="utf-8"` (m3.md trap 4 paid in advance) — keep the editor saving UTF-8 and this stays a non-event.
9. **A misspelled subject is a phantom subject.** The near-collision guard catches case and whitespace variants, but `anatomy_physiology` vs `anatomy_and_physiology` are two "legitimate" subjects, and the phantom's questions are unreachable while the Subject screen is hardcoded. Until subject buttons derive from the bank (when a second subject lands and makes phantoms visible on screen), the M5.b success check is the net: `bank.subjects` listing anything beyond the one expected entry is a typo hunt, not a new subject.
10. **The display order splits the truth in two — trap 1's sibling.** Today the click loop's `enumerate` position over the answer buttons *is* the canonical index; after the shuffle it isn't, and any code that keeps assuming so marks wrong answers correct on shuffled questions. Same cure as the scroll offset: one convention (map clicks back to canonical, or compare display slots), applied to both the popup build and the click resolution — mixing them is the bug.
11. **Shuffling in place scrambles the bank.** `next_question` returns the *same object* the bank holds — `rng.shuffle(question.choices)` corrupts it for the whole session, and the recycled ask comes back pre-scrambled with an `answer_index` that now lies. The shuffle produces a new list (or an index order) and never touches `question.choices`.
12. **When the shuffle runs is half the feature.** At load time: the order is frozen all session, so recycled questions teach positions anyway — most of the point lost. In the draw loop: the choices reshuffle every frame and dance under the cursor. Once per ask, stored with the pending question, is the only correct moment.
13. **"All of the above" is when, not if.** An 1,870-question open bank will contain positional choices, and shuffled they become nonsense that *looks* like a bug in your shuffle code. The `shuffle: false` flag is the escape hatch; the M5.f write-time glance is what keeps it applied.

## Done when

The loader names the file on syntax errors, refuses duplicate ids, and refuses near-identical same-topic subtopics — each with a test; every question carries `subject`, the bank answers `subjects` and `topics(subject)` with tests to match, and the Topics screen lists only the chosen subject's topics; the bank is split one file per topic with zero test edits needed; every ask displays its choices in a fresh shuffled order — canonical files, an untouched `Question`, seeded randomness, `"shuffle": false` honored — with the property tests to match; no subtopic is a "Filler" and no prompt is a placeholder; every subtopic holds at least 3 real, difficulty-tagged questions with the 8+ target climbing on its own clock; the Topics screen scrolls cleanly with the Start button stationary and clicks landing where the eye says; `pytest` passes; and the baseline is committed.
