# M3 — Questions: movement gets rationed

Breakdown of M3 from `implementation_plan.md` §5 (est. 6–10 hours total).

M2 ended with unconditional movement and a debug key standing in for wrong answers. M3 builds the thing the debug key was impersonating: click a square → a question appears → the answer decides who moves. Correct: the player advances onto the clicked square and Blue holds. Incorrect: the player stays and Blue flees. Exactly one side moves per question — this is the turn rule settled in `implementation_plan.md` §4, and M3 is where it becomes real. The `F` key gets the funeral m2.md scheduled for it.

This milestone has two very different halves: **data** (JSON loading, `Question`, `QuestionBank` — pure logic, fully testable, and new ground since it's the project's first file I/O) and **pixels** (word-wrapped text, buttons, the popup — pygame handwork, mostly verified by eye). The sub-goals alternate so neither half becomes a slog.

## Decisions made

- **Multiple-choice only.** Settled in `implementation_plan.md` §4: clickable answer buttons are cheap; a text-input widget is not. `fill_blank` stays a Phase 2 stretch goal, but the `type` field ships in the data format now so adding it later is additive.
- **One flat pool, topic from the data, not the filename.** `QuestionBank` loads *every* `*.json` file in `data/questions/` into one pool. Files are containers for authoring convenience (one per topic is tidy, but nothing enforces it); each question's `topic` field is the only truth about its category. Renaming a file can never recategorize a question.
- **The pure/pixel line extends.** `questions.py` never imports pygame — loading, validation, and rotation are all headless-testable, and M3.f adds the same subprocess guard that protects `board.py` and `characters.py`. `ui.py` is the opposite: unapologetically pygame, verified by eye and PNG.
- **Rotation is deterministic, like everything else in this game.** `next_question(topic)` hands out the first *unused* question in load order and marks it used. No randomness — the same discipline that made flee testable (sorted tie-breaks) makes rotation testable here. A shuffled draw is coming eventually — Phase 3's topic selection means a board might run on 1–3 topics, where deterministic order becomes obvious — but it's logged in `implementation_plan.md` §7, not built in M3.
- **A dry category recycles by reset.** When every question in a topic has been used, clear that topic's used-marks and start over. This is the "recycle oldest" policy from `implementation_plan.md` §4 in its simplest honest form — with deterministic load-order rotation, reset *is* oldest-first. Revisit only if repetition feels bad in playtesting.
- **Validate at load, crash at startup.** A malformed question (missing field, `answer_index` out of range, unknown `type`) kills the program the moment the bank loads, with an error naming the file. A typo in a data file must never survive until mid-game where it silently mislabels a right answer as wrong.
- **Cell→category assignment is game state, assigned once at startup.** A plain `dict[Cell, str]` built in `main.py`: round-robin over the bank's sorted topics, walking `board.cells()` order. Deterministic, no registry on `Board` (same reasoning as M2's occupancy decision). Randomized assignment is another knob logged in `implementation_plan.md` §7.
- **The popup is an `if`, not an architecture.** One piece of pending state ("the question being asked, and the cell at stake") switches the event handling and draw between board mode and question mode. The real state machine arrives in M4 when MENU and GAME_OVER make it three-plus states; two states don't earn it. This is m2.md trap 6 holding the line one more milestone.
- **Selection finds its meaning.** M2 trap 4 predicted it: `selected` becomes "the square whose question you're answering" — the popup's target cell, highlighted while the question is open. The M1-era "select any square" behavior retires.
- **Catching is question-gated** *(decided 2026-08-26)*. Every advance is earned, the catch most of all: clicking adjacent Blue opens a question like any move does, drawn from the category of the square Blue stands on. Correct → the catch lands (`print("caught!")` until M4 builds the win screen). Incorrect → the standard wrong-answer outcome: the player stays and Blue flees the fumbled grab — which reads exactly right, since Blue escapes adjacency. Planned evolution (playtesting-era, logged in `implementation_plan.md` §7): Blue's square temporarily *possesses a random topic* while Blue stands on it, reverting to the square's assigned topic when Blue moves off.

| File | Owns |
|---|---|
| `data/questions/*.json` | starter question content — a handful to build against (the real bank is M5's) |
| `questions.py` (no `import pygame`) | `Question` — fields, `from_dict`, `is_correct`; `QuestionBank` — directory load, `topics`, `next_question` |
| `ui.py` | word-wrap helper, `TextBox`, `Button` |
| `main.py` | cell→category dict; pending-question state; the answer gate (correct → player moves, incorrect → Blue flees); the `F` key deleted |

## Sub-goals

### M3.a — JSON: a primer and the first data file (~60 min)

- [ ] Work through the primer below in the REPL until every row of the type table has been seen firsthand
- [ ] Create `data/questions/` with a starter file — 4–6 questions in the §4 format across 2–3 topics, enough to exercise rotation and the category round-robin
- [ ] Load the file in the REPL and poke at it: what type came back? what's at index 0? how many `choices` does it have?

**The primer.** JSON is *text* — a file full of characters that happens to follow rules. Python's built-in `json` module converts between that text and live Python objects. Four functions cover everything, in two mirrored pairs: `json.load` / `json.loads` parse JSON *into* Python; `json.dump` / `json.dumps` go the other way (M3 only parses — dumping matters when a game saves state, which this one doesn't yet). The trailing `s` means *string*: `loads` takes a `str` you already have; `load` takes an **open file object** and reads it for you. Handing a file *path* to `loads` — or a path string to `load` — is the classic first-day error; the file-reading idiom is a `with` block around `open(path, encoding="utf-8")`, passing the resulting file object to `json.load`.

Every JSON value becomes a fixed Python type — this table is the whole contract:

| JSON | Python |
|---|---|
| object `{...}` | `dict` (keys are **always** `str`) |
| array `[...]` | `list` |
| string | `str` |
| number | `int` or `float` |
| `true` / `false` | `True` / `False` |
| `null` | `None` |

Toy round in the REPL to see it happen: `json.loads('{"a": [1, 2.5, true, null]}')` returns `{'a': [1, 2.5, True, None]}` — dict, list, int, float, bool, None, all from one string. Notice what's *absent* from the table: no tuples, no sets, no `Cell`, no custom classes. JSON can only ship the six shapes above; anything richer is rebuilt on the Python side after parsing — which is exactly the job `Question.from_dict` exists to do in M3.b.

Since our files hold a top-level *array* of question objects, `json.load` on one returns a `list[dict]` — and from there it's ordinary Python: index it, loop it, `len()` it, chase keys with `[...]`.

Failure comes in three layers, and knowing which layer threw tells you where to look: the file doesn't exist (`FileNotFoundError` — wrong path), the text isn't valid JSON (`json.JSONDecodeError`, which names the line and column — fix the file, and know that JSON is stricter than Python: double quotes only, no trailing commas, no comments), or the JSON parsed fine but the *shape* is wrong — a missing `"prompt"`, an `answer_index` of 9 on a 4-choice list. That third layer is invisible to the `json` module; it's ours, and M3.b builds the checkpoint for it.

**Success check:** a REPL session that loads the starter file, prints one prompt, and answers "what Python type is this?" correctly at every level of the structure without guessing.

### M3.b — `Question` (~45 min)

- [ ] `Question` in `questions.py`, fields mirroring the §4 format: `id`, `topic`, `difficulty`, `prompt`, `choices`, `answer_index`
- [ ] `from_dict(d)` classmethod — the same alternate-constructor shape as `at_start`, but fed a parsed-JSON dict instead of a board
- [ ] Validation inside construction: `type` must be `multiple_choice`, `answer_index` must index into `choices` — raise with a message that names the question `id`
- [ ] `is_correct(choice_index)` — the one question the popup will ever ask it

**Success check:** in pytest or the REPL — `from_dict` on a hand-typed dict produces a `Question`; `is_correct` is `True` at exactly `answer_index`; a dict with a missing field or out-of-range index raises before any `Question` exists.

This is the boundary checkpoint the primer promised: raw `dict`s from the JSON layer go in, trusted objects come out, and nothing downstream ever touches a bare dict again. `difficulty` is carried but not yet consulted — filtering by it has no UI until the M5/M6 era.

### M3.c — `QuestionBank` (~90 min)

- [ ] Construction takes the data directory; loads every `*.json` in sorted-filename order, `from_dict`s each entry into one flat pool — so a bad file crashes here, at startup, with the filename in hand
- [ ] `topics` — the sorted unique topics present, which is what the cell→category round-robin consumes
- [ ] `next_question(topic)` — first unused question of that topic in load order; marks it used
- [ ] Dry topic → reset that topic's used-marks and hand out the first again (the recycle decision)

**Success check:** point the bank at `data/questions/` in the REPL; call `next_question` on one topic repeatedly and watch it walk the topic in order, wrap around when dry, and never hand out another topic's question.

Design pressure to respect: the bank owns *used-ness*, questions stay immutable. Whether "used" lives as a set of ids or a per-topic structure is an implementation choice — but M2's determinism lesson applies: however it's stored, the rotation order must come out the same every run, because M3.f asserts it.

### M3.d — Words on the screen: wrap, `TextBox`, `Button` (~2 h)

- [ ] A word-wrap helper: given text, a font, and a max pixel width, return the list of lines that fit
- [ ] `TextBox`: draws wrapped lines stacked at a position — the popup's prompt area
- [ ] `Button`: a rect and a label; can draw itself and answer "does this point hit me?"

**Success check:** a throwaway script that renders a long sentence into a narrow box — no line escapes the width, no word is split mid-letters. Run it windowed, or use the `SDL_VIDEODRIVER=dummy` + save-a-PNG trick to check it headless.

This is scope trap 1 from the plan (`font.render` gives exactly one line) paying its bill. The wrap algorithm in words: split the text into words, then greedily build lines — keep a current line, and for each word ask the font how wide *current line + this word* would be; if it fits, append, if not, the current line is finished and the word starts the next one. The measuring tool is `font.size(text)`, which returns rendered dimensions **without** rendering — that's the whole trick. Wrapping by character count instead of measured pixels is the classic mistake; proportional fonts make "40 characters" two different widths in two different sentences. `Button` needs no callback machinery: the popup will simply ask each button whether the click landed on it — `pygame.Rect.collidepoint` is the hit test, the same pixel-geometry family as M0's `pixel_to_cell`.

### M3.e — The popup and the gate (~90 min)

- [ ] At startup: build the cell→category dict (round-robin `bank.topics` over `board.cells()`)
- [ ] Clicking a legal-move square no longer moves — it stashes the pending state (target cell + `next_question` for that square's category) and the popup takes over
- [ ] While a question is pending: board clicks and hover go dormant; draw the popup (TextBox prompt, one Button per choice) over the board; `selected` marks the square at stake
- [ ] The catch goes through the same popup: clicking adjacent Blue stashes a pending question too, drawn from the category of Blue's square — the target being Blue's cell is what marks the intent as a catch, since that cell can never be a legal *move*
- [ ] Answer click resolves it by intent: correct on a move → `player.move_to(target)`; correct on a catch → `print("caught!")`, the player stays put; incorrect on either → Blue flees exactly as the `F` key did; every path clears the pending state and the board wakes up
- [ ] Delete the `F` key handler — M3 exists; the scaffolding comes down

**Success check:** every legal move and every catch attempt now costs a question; a right answer walks the player onto the square (or lands the catch) while Blue holds; a wrong one leaves the player put and sends Blue running — off a fumbled catch, that means Blue breaks adjacency and must be cornered again; the highlight set, the popup, and the movement never disagree; and `grep F main.py` finds no debug key.

The click handler's decision ladder grows one honest rung — catch → *ask* → select — and the `elif` chain from M2 should still read as one ladder. If wiring the popup makes `main.py` feel crowded, that's the M4 state machine knocking, right on schedule: note the pain and resist, same as M2 did.

## Traps

1. **`load` vs `loads`.** `loads` parses a string; `load` reads an open file object. Handing a path to either is the error you'll hit first. The `s` is "string" — read it that way every time.
2. **JSON keys are strings, and there are no tuples.** A `dict[Cell, str]` cannot round-trip through JSON as-is — keys would need encoding into strings and rebuilding on load. M3 dodges this (the cell→category dict lives and dies in memory), but the trap springs the day saving game state, so it's recorded here.
3. **Trust nothing at the boundary.** The `json` module guarantees valid JSON, not valid *questions*. Every field access on an unvalidated dict is a landmine; `from_dict` is the single checkpoint where dicts become objects, and nothing past it handles a bare dict. Same one-gate principle as `legal_moves`.
4. **`encoding="utf-8"`, explicitly, every `open`.** Science questions will carry `°`, `µ`, `H₂O`. The platform-default encoding works until the exact moment it doesn't — on someone else's machine, in CI.
5. **`font.size` measures, `font.render` draws.** Wrap by measured pixels, never by character count. And measure *word by word* — measuring the whole text tells you it doesn't fit, not where to break it.
6. **The popup is not a state machine.** One pending-question value and an `if` in the event handling and draw paths. MENU and GAME_OVER will force the real architecture in M4; building it now means building it twice.
7. **Shared mutable banks poison tests.** `next_question` mutates used-state, so a bank shared between tests makes them order-dependent — the second test inherits the first one's history. Every test builds its own bank from its own `tmp_path` files. (Flee dodged this by being pure; the bank can't, so the tests carry the discipline instead.)
8. **Two intents, one popup — resolve them deliberately.** A pending move and a pending catch look identical while the question is open; they differ only at resolution. A correct *catch* must not fall through into the generic "move onto target" branch — Blue's cell is occupied, and walking the player onto it violates the occupancy rule every other line of the game respects. The tell that keeps this honest: the catch target is never in `legal_moves`, so any resolution logic keyed on "target was a legal move" silently drops the catch. Decide the intent when the question is *stashed*, not by re-deriving it at answer time — Blue may be mid-flee-history by then in later milestones.

## Done when

Clicking a legal square opens a question drawn from that square's fixed category; a correct answer moves the player there, an incorrect one holds the player and sends Blue one flee step; clicking adjacent Blue opens a question the same way, with a correct answer landing the catch and a wrong one letting Blue break away; questions within a category rotate and recycle instead of repeating or running dry; the popup's prompt wraps inside its box and the answer buttons click reliably; the `F` key is gone; `questions.py` is pygame-free with a guard test proving it; `pytest` passes with the new `test_questions.py` suite; and the work is committed.
