# M6 — Polish: the game gets played

Breakdown of M6 from `implementation_plan.md` §5 (plan estimate 4–8 hours for "playtesting, bug fixes, visual cleanup"; the scope settled 2026-09-06 below is bigger — see the budget note at the end of this intro).

M5 ended with a finished machine and a real bank: 1,595 questions, fourteen topics, every screen in place. What's missing is everything you only notice by *playing*: the popup vanishes before you see whether you were right, Blue always sidesteps the same direction, every fresh boot opens on the same questions, and the whole thing wears M0's placeholder rectangles. M6 is where the game stops being a working program and starts being something a student would choose to open.

**Order of work, settled 2026-09-06: mechanics first, visuals second.** The §7 knobs at the bottom of `implementation_plan.md` are the mechanical half — they change what's on screen (the reveal adds a whole phase to the popup), so polishing the visuals first means polishing twice. Bug fixes from playtesting land whenever they're found, in ordinary commits, and don't need a sub-goal.

**Budget, honestly.** The sub-goals below add to roughly 10–15 build hours against the plan's 4–8, because three §7 knobs moved in on purpose (a fourth was declined). Two things make that fine: each sub-goal is independently shippable, so the milestone can stop after any of them and still be "polish"; and the visual half is timeboxed by decision, not open-ended. The 30-hour Run-from-Red gate is measured against build hours, and it's a *gate*, not a deadline — a finished, good-looking Catch Blue that misses it is the better portfolio piece (§5 says so already).

M5's content treadmill keeps running in the background: the 177-entry rewrite queue and the thin Aging subtopics (see `question_bank_tracker.md`) are tutoring work on their own clock and don't gate anything here.

## Decisions made

- **Mechanics before visuals** *(David, 2026-09-06)*. See above. The knobs that ship: randomized question rotation, randomized flee tie-breaks, and the answer reveal. Ordered small-to-large so the two one-hour randomness fixes warm up the seeded-`Random` test discipline the reveal leans on. (A fourth — Blue's square possessing a random category — was scoped in, then declined after M6.c; see below.)
- **The reveal is a phase, not a pause** *(§7 knob, mechanism settled 2026-09-01; timing settled here)*. After the player clicks an answer, the popup stays up for a short reveal — chosen button colored green or red, the correct answer highlighted whenever the pick was wrong — and *then* the consequence applies (move, flee, or the end-screen transition). The timer accumulates across frames from the loop's clock, never a blocking `pygame.time.wait`, which would freeze the entire game mid-frame. Clicks during the reveal are ignored. The duration is one constant, and it's injectable so tests can zero it. For a study tool this is the highest-value change on the list: "wrong, *and here's the right answer*" is exactly the feedback the game currently swallows.
- **PLAY gains a third mode.** Today PLAY is two modes: board (`pending is None`) and question (`pending` set). The reveal is a third — *answered but unresolved* — and it must be its own explicit condition, not inferred from `pending` being half-cleared. Whatever represents it, the click handler's job shrinks to "record the answer and start the clock"; the consequence block moves behind the timer. That split is also the moment m4.md's parting note comes due: the resolution logic (correct → move or catch, wrong → flee, decrement, win-before-loss) is now a self-contained step worth extracting into a pure function that a test can call without pygame — consider it, don't force it.
- **Question rotation becomes a shuffled draw** *(§7 knob)*. `next_question` currently walks each pool in file order — testable, but every app boot opens identically and a player learns "the first Organelles question is always the mitochondrion one." The change: within a (topic, subtopic) pool, draw from a shuffled order and reshuffle on recycle. The randomness comes from an injected `random.Random`, same as `assign_cell_topics` and `display_order` — never module-level `random`. The bank is built in `main.py` before `Game` exists and `Game` owns the rng, so *where the rng enters the bank* is a small design question with two honest answers (the bank takes an rng at construction; or `next_question` takes one per call, as `display_order` does). Pick one; don't create a second `Random` instance in the process (trap 4).
- **Flee tie-breaks randomize among improving candidates** *(§7 knob)*. `flee_step` picks `max(sorted(survivors), key=distance)` — deterministic, so a threat from below always sends Blue the same way. The change: among candidates tied for best distance, pick one at random via an injected rng. m2.md's corrected note still holds: every orthogonal step changes Manhattan distance by exactly ±1, so the only ties that exist are among *improving* moves — the randomness added is exactly that set and nothing else. Cornered behavior is unchanged (no survivors → stay put).
- **Blue's square holding a random category — declined** *(David, 2026-09-06, after M6.c)*. The §7 knob planned since 2026-08-26 is not shipping in M6. Reasoning: M3 settled that labels are drawn so choosing a square is an informed decision, and hidden possession replaces the endgame's routing strategy with luck — the wrong trade for a study tool; re-rolling the category on every flee softens a failed catch rather than sharpening it; and with M6.a's shuffled rotation the specific catch question is already unpredictable, so possession stacks category randomness on question randomness for one question. The itch it was meant to scratch ("the catch should test more than one known square") has a better lever: difficulty scaling with proximity to Blue — logged in `implementation_plan.md` §7 for once the bank is graded. If playtesting finds players herding Blue onto an easy square, the cheap fix is drawing the label under Blue (view-only), not possession.
- **Difficulty grading stays content, not code** *(reaffirmed)*. Playtesting is when questions start showing which ones bite; note them as you go, grade them in the JSON on the treadmill's clock. Nothing in M6 reads `difficulty`, and the §7 rule holds: no difficulty-filtered drawing on ungraded data.
- **Knobs are tuned last, with everything else landed.** Move limit (20), board size (5×5), and wizard back buttons are M6.e questions, answered by playing the finished mechanics — not before. The plan's advice stands: if Catch Blue needs a difficulty setting, try board size before touching flee rules.
- **Visual polish picks a style first, then executes inside a timebox** *(David, 2026-09-06 — style undecided as of writing)*. The resource overview under M6.f is the menu; the decision is a single sentence written into this doc before any asset is made or downloaded. Whatever the style, two constraints carry over from earlier milestones: the palette stays colorblind-safe (the current player orange and Blue's blue are already Okabe-Ito colors — keep that property when the palette grows), and every external asset gets a license line, the same way every question does.
- **Out of scope, still:** Red, the 9×9 board, fill-in-the-blank input, sound beyond a stretch bullet in M6.f, pygbag/PyInstaller packaging, and any state-machine ceremony (`on_enter`/`on_exit`, stacks) the reveal doesn't strictly need.

| File | Owns |
|---|---|
| `game.py` | the loop hands the current state a time step each frame (an `update` call alongside `handle_events`/`draw`, or the state reads the clock — see M6.c) |

## Sub-goals

### M6.a — Randomized question rotation (~60 min)

- [x] `next_question` draws from a shuffled order within the (topic, subtopic) pool; the pool reshuffles when it recycles
- [x] Randomness comes from an injected `random.Random` — per-call, threaded from the one instance `Game` already owns
- [x] The existing rotation contract survives unchanged: no repeat until the pool is exhausted; used-marks still carry across replays; `shuffle: false` and `display_order` are untouched (that's *answer* order, a different thing)
- [x] Tests: with a seeded rng, one full pass through a pool yields each question exactly once; the same seed gives the same sequence; different seeds produce varied sequences; the recycle still serves every question again before repeating

**Success check:** boot the game twice on the same single topic; the first questions differ. `pytest` green — and note which old rotation tests had to change from "first is `q1`" to "first is *one of* the pool": that's the exact-order assumption being retired, on purpose.

**Shipped 2026-09-06.** `next_question(topic, subtopic, rng)` takes the RNG per call, matching `display_order`; `PlayState` passes `self.rng`, so neither startup order nor RNG ownership changes. The bank lazily stores a shuffled list per pair while `used_ids` remains the usage state. Exhaustion clears only that pool's marks and reshuffles its list. Both survive replay. Canonical loaded order and answer data are unchanged. A repeat across a cycle boundary, or an identical reshuffle, is allowed; no extra anti-repeat rule was added.

**Validation:** 71 question tests and 158 full-suite tests passed. Coverage includes complete cycles across seeds, reproducibility, seed variation, initial/recycle shuffle calls, pool isolation, session continuity, singleton/unknown pools, and canonical-data preservation with `shuffle: false`. Retired the exact-order assumptions in `test_rotation_walks_the_pool_in_load_order`, `test_dry_pool_recycles_from_the_top`, and the hardcoded B-pool sequence in `test_recycle_resets_only_its_own_pool`. A headless single-topic synthetic-click check passed for movement, wrong catch/flee, final-move win, rendering, replay persistence, and continued drawing. Interactive two-boot observation remains a manual check; matching first questions can occur legitimately.

*Verified 2026-09-06 (Claude): full suite 158 passing. Independently on the real bank — 20 seeded boots on `cells` produced 20 distinct first-question sets; a pool's two consecutive cycles each covered every id with differing orders; canonical `bank.questions` order untouched; the cycle-boundary repeat rate measured 0.088 over 2,000 trials, matching the 1/11 expected for an 11-question pool (accepted, per the shipped note). Headless full-flow over 10 seeds: win → replay → win with the same `QuestionBank` and the same `Random` instance across the replay and no id repeated across both games. The M5.e reference driver in `question_sources/verify_shuffle_e2e.py` was updated to the new signature and still passes.*

This is the first sub-goal because it's the smallest possible version of the discipline every later one uses: randomness in, seed it in tests, assert membership or seeded equality instead of a fixed value. Get the pattern right on 30 lines before the reveal asks for it on 300.

### M6.b — Randomized flee tie-breaks (~45 min)

- [x] `flee_step` takes an rng and, among candidates tied for the best distance, picks one at random
- [x] Cornered Blue still stays put; a single improving candidate is still chosen deterministically (there's nothing to randomize)
- [x] `PlayState` passes its rng through — the only call site
- [x] Tests: the chosen cell is always in the tied-best set (a seed sweep, not one run); a cornered Blue still returns its own cell; the 600-pairing full-board sweep from M2 still asserts "distance never decreases" rather than an exact cell

**Success check:** stand the player directly below Blue in open board and repeat the wrong answer across several games — Blue should sometimes go left, sometimes right, sometimes up. Before this change it was always the same.

*Verified 2026-09-06 (Claude): full suite 189 passing. `flee_step(board, threat, rng)` sorts the tied survivors before `rng.choice`, short-circuits a single survivor and the cornered case without touching the rng (tested via `getstate`), and `PlayState` is the only call site. The doc's success check driven headlessly through the real play state — player at (2,4) below Blue at (2,2), wrong answer, 60 seeds — sent Blue left 20, right 24, up 16 times, and never moved the player. The 600-pairing sweep now asserts the full contract (improving step when one exists, else stay) across 10 seeds.*

The M2 tests were written to assert exact cells *because* the chooser was deterministic; the note in §7 predicted they'd need to become membership assertions, and here they do. If a test can't be rewritten as "in the tied set," it was asserting an accident of `sorted`, not a rule.

### M6.c — The answer reveal (~2–3 h)

- [x] The state interface gains time: either `Game.run` passes each frame's elapsed milliseconds (the value `clock.tick` already returns) into a new per-state `update` call, or the play state reads `pygame.time.get_ticks()` itself — pick one and note why here
- [x] Clicking an answer records the pick and starts the reveal instead of resolving immediately; the popup stays drawn
- [x] `Button` accepts a highlight override; during the reveal the chosen button shows green (correct) or red (wrong), and on a wrong pick the correct button also shows green
- [x] Clicks (board or popup) are ignored while the reveal runs; hover doesn't change either
- [x] When the timer expires the consequence applies exactly as today — move or hold, flee, counter decrement, win-before-loss, `GameOverState` handoff — and the popup tears down
- [x] `REVEAL_DURATION` lives in `constants.py` and is overridable on `PlayState` so tests can set it to zero (or tick past it)
- [ ] Optional, recommended: the consequence block becomes a pure `resolve_answer`-style function (inputs: correctness, intent, positions, counter; outputs: new positions, new counter, result or none) with a unit test for win-before-loss — the M4.f note coming due

**Success check:** answer wrong on purpose — your button turns red, the right answer turns green, the board is frozen for the reveal, and *then* Blue flees. Answer right on the final move as a catch — green, pause, "You caught Blue!" (win checked before loss, still). Mash clicks during the reveal — nothing double-fires. Then run the synthetic-click driver with duration zero and confirm the M5.e sweep still passes unchanged.

**Shipped 2026-09-06.** The `update(dt_ms)` shape: `Game.run` now ticks the clock at the top of the frame and passes the elapsed milliseconds to the current state's `update` before `handle_events`, with the four non-play states carrying a no-op — chosen because it makes the reveal drivable in tests (`update(REVEAL_DURATION)`) without any wall-clock dependence. The reveal is an explicit `AnswerReveal` value (canonical pick + elapsed) on `PlayState`; `handle_events` returns early while it exists, and the consequence lives in `_resolve_pending_answer`, called from `update` on expiry (or immediately from the click when the duration is zero). Two rules a future synthetic-click driver must know: if `update` switches state, `Game.run` skips `handle_events` for that frame so stale events never reach the new state; and the frame on which the reveal expires *discards its event batch* (those clicks landed on the reveal), so after ticking past the duration the *next* `handle_events` call is swallowed by design. The optional pure `resolve_answer` extraction was not done — the consequence is a method on the state, tested through it.

*Verified 2026-09-06 (Claude): full suite 219 passing with and without `SDL_VIDEODRIVER=dummy` (new `tests/test_game.py`, `test_play.py`, `test_ui.py`). Independently, a frame-faithful headless run through the real `Game`/`PlayState` — wrong answer froze board, counter, and both characters for the whole duration while mashed answer/board/Blue clicks did nothing, a stale click on the expiry frame was discarded, then Blue fled; correct answer highlighted only the chosen button and moved the player after expiry; final-move catch produced win after the reveal and final-move miss produced lose. Rendered frames of both reveals reviewed. The M5.e reference driver in `question_sources/` needed `reveal_duration_ms=0` (trap 3, on schedule) and passes again.*

Two shapes for the timer, and the pick is yours. An `update(dt)` on every state is the textbook game-loop shape and makes the reveal trivially testable ("call `update(REVEAL_DURATION)` and assert the consequence happened") at the cost of four states growing a no-op method. Reading `get_ticks()` inside the play state touches nothing outside `play.py` but ties the test to wall-clock time unless the duration is zeroed. Either way, the reveal's *state* is the real work: `pending` set plus a recorded pick plus an elapsed counter is one honest representation; a small enum or string mode (`"board"`, `"question"`, `"reveal"`) is another. What matters is that the draw code, the click handler, and the timer all agree on one source for "which mode are we in" — trap 2 is m5.md's trap 10 wearing a new hat.

**The modularity rule, stated once: a theme is data, primitives are the only code that draws, and states never touch pygame's drawing API directly.** A new look is a new theme value; a new *kind* of thing to draw is a new primitive. If a design idea needs anything else, it's either not a visual change or the primitives are missing one — and the count should stay under ten. Anything beyond this (abstract surfaces, abstract events, plug-in loaders) is an engine, and this project doesn't build engines. This shape is also the port-friendly one from the note below: the Go version reads the same theme data and reimplements the same handful of primitives.

#### M6.f.8 — Legal-move cue: lighter face plus a lifted tile *(David's design, 2026-09-07; break-out by Claude)*

**What's wrong:** on the pixel theme, `cell_move` and `cell` share the same face color, so a legal move is signalled only by the `cell.move` slice's thin blue outline. It's faint in normal vision (compare the two cells beside the player in `05_play_hover.png`) and disappears under protanopia. The M3 rule was that choosing a square is an informed decision; the student has to *see* the choices first.

**The design** *(David)*: legal-move tiles get a **lighter face** and sit **lifted about 2 px** above the board while nothing is hovered. Hovering a legal tile makes it **pop out a few pixels more**, smoothly. Clicking it **sets it down** under the existing selection outline, and it stays pressed while its question is up; when the answer resolves, the new legal cells rise. Three states told by geometry — raised, popped, pressed — which is exactly the cue that survives colorblindness, with the lighter face as the at-a-glance baseline underneath it.

**Feasibility** *(Claude)*: high, ~2–3 h with tests. Three things to know before building:

- *Pixel motion is stepped.* At skin scale 2 every lift is an even number of screen pixels, so a pop from 2 to 6 px is two or three visible steps over ~120 ms — a snappy pop, not a glide. That suits the style; sub-pixel motion would blur the tiles. Round the tweened value to the skin scale, never draw at fractional offsets (trap 9's cousin).
- *The lift is cosmetic.* Hit-testing stays on the grid via `pixel_to_cell`; the lifted rect is only ever drawn. Two rects for one cell is the two-truths mistake, and the "model moves instantly, the view catches up" rule from the tools section applies.
- *Flat stays byte-identical.* Lift amounts and the pop duration are theme data defaulting to zero, so the flat gallery must still match `flat-1600x900-baseline` after this ships — that's the refactor-safety check, same as f.2.

**Where it lives** — theme is data, the primitive draws, the view animates, the state forwards time:

- [ ] `theme.py`: a small frozen `CellLift` (rest_px, hover_px, pop_ms) on `Theme`, all zeros by default; `PIXEL` sets rest 2, hover 6, pop ~120 ms. A lighter `cell_move` face for pixel — either a distinct palette color drawn under the slice or a lighter pack tile as the `cell.move` slice; pick by luminance, not hue.
- [ ] `render.cell` gains a `lift` argument. Lifted drawing is: fill the grid rect with a dark socket color (`panel_line` or the pack's darkest slate), then draw the tile at the rect moved up by `lift`, so the socket's bottom strip shows as the tile's thickness. Nothing else in `render.py` changes; hover and selection rings still draw at the grid rect.
- [ ] `board_view.py`: a per-cell lift value and a target per cell (hover → hover_px, legal → rest_px, otherwise 0; pressed/selected → 0). An `update(dt_ms)` on the view moves each value toward its target by the theme's rate (linear is fine at these sizes; ease-out if it feels mechanical). `draw` passes the lift to `renderer.cell` and shifts the label rect by the same amount. Draw lifted tiles *after* their neighbors so the pop overlaps the cell above, and draw entities after tiles as today.
- [ ] `states/play.py`: forward `dt_ms` to the view from `PlayState.update` (the reveal branch returns early today — the view's update must run before that return so tiles keep settling during a reveal). `hovering` and `selected` already exist and already clear when the popup opens; the view reads them, so the state's click handler doesn't change.
- [ ] Decide the hover ring: try the pop alone first; if it reads weak, keep the ring as well. Either way the selection ring stays — it's the pressed tile's frame.
- [ ] Optional, worth one look: lift Blue's tile when the player is adjacent, since the catch is a click on that tile and it has no legal-move styling today.

#### Style directions worth considering

None of these is recommended over the others — it's the decision the first checkbox asks for.

1. **Refined flat/vector.** Keep drawing with `pygame.draw`, but deliberately: a real palette, rounded corners (`pygame.draw.rect(..., border_radius=…)`), anti-aliased circles (`pygame.gfxdraw.aacircle` / `filled_circle`), a proper font, consistent spacing. Cheapest by far, no external assets, no licensing. The characters can stay abstract shapes with a small face or icon overlay. Lowest risk to the timebox.
2. **Pixel art.** Sprites for Player and Blue, tiled cell backgrounds, a pixel font. Charming, and a huge free-asset ecosystem. Draw sprites small (16–64 px) and upscale with `pygame.transform.scale` (nearest-neighbor — *not* `smoothscale`) by an integer factor so pixels stay crisp; at 128 px cells a 32 px sprite at 4× works.
3. **Icon-driven.** Vector icons (organs, bones, neurons) as topic markers on cells and as character glyphs — fits an A&P study tool unusually well. Icons need recoloring to the palette (load as white-on-transparent, tint with `Surface.fill(color, special_flags=pygame.BLEND_RGBA_MULT)`).
4. **Illustrated / painterly.** Hand-drawn or commissioned art for the dog, the board, the menus. The most distinctive and the most expensive; only sensible if David enjoys drawing or has art on hand.

Whichever is chosen, `pygame.SCALED` at 1280×720 logical means assets are designed once at logical size and scaled by pygame to the real display — no per-DPI variants.

#### Tools already in pygame-ce

- **Shapes:** `pygame.draw.rect` with `border_radius` (and per-corner radii), `width` for outlines; `pygame.gfxdraw` for anti-aliased circles/polygons.
- **Fonts:** `pygame.font.Font("assets/fonts/X.ttf", size)` loads any TTF/OTF; `pygame.freetype` is the richer alternative (rotation, per-glyph metrics) if ever needed. Render once and cache when a string is static — board labels are the obvious candidate, per the §7 note about re-wrapping every frame (measure first; a custom TTF is slower to render than the built-in default).
- **Images:** `pygame.image.load(path).convert_alpha()` once at startup; `pygame.transform.scale` (pixel art) or `smoothscale` (everything else) once at load, never per frame; sprite sheets are just `Surface.subsurface` rectangles.
- **Transparency and overlays:** `Surface.set_alpha` or an RGBA surface blitted over the board dims it behind the popup — a one-line "focus" effect.
- **Motion:** a tween is just interpolation over time using the same `dt` the reveal introduces; `pytweening` (MIT) supplies easing functions if hand-rolling them isn't the point. Keep any animation purely cosmetic — the model moves instantly, the view catches up.
- **Sound (stretch):** `pygame.mixer` plays `.ogg`/`.wav`; short blips for click, correct, wrong are the whole budget.
- **UI libraries — probably not:** `pygame_gui` and `pygame-menu` (both MIT) provide themed widgets, scroll containers, and text entry, but they replace `Button`/`Checkbox`/`TextBox` wholesale, bring their own event model, and their theme systems are a learning curve of their own. The one argument for them is free text input for Phase 2's fill-in-the-blank. On balance, the widgets built in M3–M5 are the project's own OOP practice — restyling them is the point; replacing them is scope.

## Traps

1. **`pygame.time.wait` inside the click handler.** It looks like a one-line reveal. It freezes the loop: no drawing, no event processing, the OS thinks the window hung. The timer must be state that advances per frame.
2. **A third mode inferred from half-cleared fields.** If "in reveal" means "`pending` is set but `answer_buttons` is empty" or some other accidental combination, the draw code and the click handler will disagree eventually. Name the mode; check the name.
3. **Tests that assume click → consequence in one step.** Every synthetic-click driver written so far asserts the player moved *in the same call*. After M6.c that's only true with a zero duration or an explicit tick. Make the duration injectable before touching the tests, or every red test is ambiguous.
4. **Two `Random` instances.** The bank is built before `Game`; `Game` builds the rng. If M6.a solves that by giving the bank its own `Random()`, tests that seed the game's rng no longer control rotation, and the "same seed, same game" property silently dies. One instance, threaded through — or `next_question` takes it per call.
5. **Exact-cell flee tests that "just need the seed changed."** A test that passes only for one seed is asserting an accident. Rewrite as membership in the tied set; keep exact assertions only where the set has one element.
6. **Possession by mutation** *(moot while M6.d is declined, kept for the record)*. If possession ever returns: writing into `cell_topics` and writing back on flee is two truths; derive it instead. And `BoardView.draw` skips labels for occupied cells, so any label under Blue needs the view taught to draw it.
7. **Restyling before the reveal exists.** The popup gains two colors and a frozen phase in M6.c; the end panel is drawn over the play state. Styling either before the mechanics land means redoing it.
8. **Per-frame font rendering with a real TTF.** `Font(None)` is fast; a loaded TTF at 25 labels × 60 fps is where the §7 label-cache note stops being theoretical. Measure with the new font before building a cache; build the cache only if the frame time shows it.
9. **`smoothscale` on pixel art.** It blurs. Pixel art scales with `transform.scale` by integer factors; everything else with `smoothscale`. Scale once at load, never in `draw`.
10. **Assets without a license line.** The same rule as questions: nothing lands in `assets/` without a source and license recorded. CC BY needs attribution *in the shipped game* (a credits line on the Game Select screen is enough); CC0 doesn't, but recording it anyway makes the audit trivial.
11. **Magic numbers multiplying under a redesign.** `popup_left = 720`, `PANEL_TOP = 40`, `CHECKBOX_LEFT = 380` — fine while there's one look. A restyle that changes spacing wants those in `constants.py` next to the colors, one definition each, or the fourth screen will drift from the first three.
12. **The timebox is real.** The style checklist has no bottom. When the hours are spent, the current state ships and the rest goes in the playtest log.
