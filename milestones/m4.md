# M4 — Game flow: it becomes a game

Breakdown of M4 from `implementation_plan.md` §5 (est. 8–12 hours; the menu flow settled 2026-08-31 is bigger than the plan's original "menu" line item).

M3 ended with a playable *loop* but not a *game*: the program boots straight onto the board, the catch is a `print`, and nothing ever ends. M4 adds everything around the loop — a three-screen menu flow into the game, a win, a loss, and replay — and pays the architectural debt M2 and M3 deliberately took on: the state machine arrives. Two milestones of "note the pain and resist" end here, on schedule.

The menu flow and end screens (settled 2026-08-31):

```
GAME_SELECT ──► SUBJECT ──► TOPICS ──► PLAY ──► GAME_OVER ──► (replay: PLAY)
                                                    └────────► (main menu: GAME_SELECT)
```

- **Game Select:** "Catch Blue", "Run from Red (coming soon)" — the latter visibly inactive.
- **Subject:** "Anatomy & Physiology", "Organic Chemistry (coming soon)" — the latter visibly inactive.
- **Topics:** checkboxes — "All" plus one per topic in the bank, prettified from the data; a Start button leads directly into the game.
- **Lose screen:** "Blue got away!" with a "Try again" button. **Win screen:** "You caught Blue!" with a "Play again" button. Both carry a "Main Menu" button back to Game Select. Replay keeps the chosen options and re-scrambles the board.

## Decisions made

- **The state machine is real now** *(the M2/M3 promise coming due)*. A `Game` class owns the window, clock, and loop, and delegates events and drawing to the current state object. Five states: `GAME_SELECT`, `SUBJECT`, `TOPICS`, `PLAY`, `GAME_OVER`. The machine is an attribute holding the current state and a way to switch — no transition tables, no state stacks, no framework. Three-plus screens is what earns a state machine; nothing here earns more than the minimum one.
- **The question popup stays an `if` inside PLAY.** The plan's §4 diagram drew QUESTION as a sibling state, but the popup is an *overlay* on a live board, not a screen that replaces it — promoting it would force PLAY's drawing into a second state for no behavioral gain. M3's pending-question mechanism moves into the PLAY state intact. (GAME_OVER, by contrast, *is* a screen of its own, even though it also draws the final board underneath its panel.)
- **Menus assemble a config; the game consumes it.** The wizard's product is a small config value — mode, subject, the selected topic list — handed to PLAY at start. "Try again" / "Play again" reuse the same config with a fresh scramble; "Main Menu" discards it and returns to GAME_SELECT. The game never reaches back into menu objects, and menus know nothing about boards.
- **The wizard is forward-only in M4.** No back buttons between menu screens; the only backward edge is Main Menu from the end screens. Three quick screens make mis-clicks cheap to redo. Add back buttons later if playtesting says otherwise — logged, not built.
- **Topic checkboxes come from the bank, prettified** *(decided 2026-08-31)*. The Topics screen lists `bank.topics` transformed for display — `anatomical_language` → "Anatomical Language" (underscores to spaces, title case). One source of truth: adding a topic to the JSON adds its checkbox with no menu edit. The screen keeps (raw, display) pairs side by side so the config carries *raw* topic identifiers — display strings never travel into game logic.
- **The Subject screen is cosmetic for now** *(decided 2026-08-31)*. Everything in `data/questions/` is Anatomy & Physiology, so selecting the one active subject filters nothing. The real mechanism — a `subject` field per question vs. a subdirectory per subject — is deliberately undecided until Organic Chemistry content exists; deciding it today means guessing. Logged in `implementation_plan.md` §7.
- **Every game start scrambles the board** *(decided 2026-08-31)*. The cell→(topic, subtopic) assignment is shuffled — first game and replays alike, one code path. This flips the §7 "randomized cell→category assignment" knob and is the project's first real randomness. Balance survives the shuffle: build the pair list by cycling the selected topics' pairs up to 25 entries, *then* shuffle, so every pair appears as evenly as 25 cells allow. Use a `random.Random` instance the setup code is handed, not the module globals — a seeded instance is what makes M4.f's tests assertable, the same discipline that made flee and rotation testable.
- **The move limit is 20, and every answered question consumes one** *(decided 2026-08-31)*. Right or wrong, move or catch — closing a question costs a move. Wrong answers therefore burn a move *and* trigger the flee, so accuracy is doubly punished, and a struggling player always reaches the loss instead of stalling forever. The count decrements at answer resolution, not at click. 20 is a default, not a design: difficulty presets or user-facing tuning are §7 material.
- **Remaining moves are visible during play** *(decided 2026-08-31)*. A counter in the side column. A hidden loss timer feels unfair — the player should see the pressure they're under.
- **The bank survives replays.** One `QuestionBank` lives for the whole app session; used-marks carry across games, so a replay serves fresh questions until pools run dry and recycle. Resetting the bank per game would replay the same opening questions every run — worse for studying, which is the point of the game.
- **Win before loss, always.** The 20th question answered correctly on a catch is a *win*, not a loss — check the catch result before the move counter. The order of those two checks is the difference between a triumphant finish and a robbery.

| File | Owns |
|---|---|
| `game.py` | `Game` — window, clock, loop, current-state switching; the state interface (handle events, draw) |
| `states/menus.py` | the three menu screens: Game Select, Subject, Topics (checkbox list + Start) |
| `states/play.py` | M3's board + popup behavior, relocated; the move counter and its display; win/lose detection handing off to GAME_OVER |
| `states/game_over.py` | the end panel: result text, Try/Play again, Main Menu |
| `game_setup.py` (no `import pygame`) | pure helpers: topic prettify, the balanced scrambled cell→pair assignment |
| `ui.py` | `Button` grows an inactive look/behavior; new `Checkbox` |
| `main.py` | shrinks to a thin entry point: build the bank, build `Game`, run |

## Sub-goals

### M4.a — The state machine, by refactor only (~90 min)

- [x] `Game` class in `game.py`: window, clock, the loop, a `state` attribute, and delegation — each state gets events and a draw call
- [x] One state to start: PLAY, containing *exactly* what `main.py` does today — the board, the popup `if`, the gate — moved, not modified
- [x] `main.py` becomes the thin entry point the plan always intended
- [x] Every existing test stays green, and the game plays identically to M3

**Success check:** `git diff` shows code *moving*, not changing — the popup logic, the decision ladder, and the draw calls should be recognizable line-for-line. If behavior changed during the move, two things changed at once and neither is verified.

The refactor comes first and alone, because moving code and changing code in the same step is how working code breaks untraceably. When PLAY runs identical to M3-main, every screen added after it is a purely additive step. This is the milestone's foundation — rush it and every later sub-goal wobbles.

## Traps

1. **Refactor and features in the same step.** M4.a moves code without changing it, alone, verified green, *before* any screen exists. Interleave the move with new behavior and a break has two possible causes forever.
2. **A state machine that grows features.** No transition tables, no stacks, no `on_enter`/`on_exit` ceremony until a state actually needs it. Five states and an attribute assignment is the whole architecture. The moment the machine gets clever, M2's trap 6 has won after all.
3. **Display strings leaking into logic.** "Anatomical Language" is for pixels; `anatomical_language` is for the bank and config. The Topics screen holds both and hands the raw one onward — the same identifier-vs-display line M3 drew for subtopics, now applied to topics.
4. **`title()` is dumber than it looks.** It would render a hypothetical `dna_structure` as "Dna Structure". Current topics survive it fine; if one ever doesn't, the fix is an explicit display-name map, not a cleverer transform.
5. **Module-global randomness is untestable randomness.** Pass a `random.Random` into the assignment helper. Tests seed it; the game feeds it an unseeded one. Same lesson the flee tie-break note in §7 already carries.
6. **Reset by rebuilding, not by patching.** Replay constructs a fresh PLAY — new assignment, new characters, new counter. Mutating the old state's fields back to defaults *will* miss one eventually (the M3-era `pending`/`selected`/`popup` cluster is exactly the kind of thing that lingers). The bank is the one deliberate survivor, and it survives by living outside PLAY, not by being skipped in a reset.
7. **Win/loss check order.** Catch first, counter second. A correct catch on move 20 is a win. Write the test-by-eye scenario before writing the branch.
8. **Inactive is a state, not an absence.** "(coming soon)" buttons must render differently *and* reject clicks. Just skipping the handler leaves a normal-looking button that ignores the user — indistinguishable from a bug.
9. **The bank must not be rebuilt on replay.** Reconstructing `QuestionBank` resets every used-mark and every replay opens with the same questions. Build it once in `main.py`, hand it down.

## Done when

Booting lands on Game Select; the wizard runs Game Select → Subject → Topics with the inactive options visibly dead; the Topics checkboxes derive from the JSON (with "All" behaving), and Start requires a selection; the game starts on a scrambled board wearing only the chosen topics, with remaining moves visible; every answered question costs a move; a correct catch shows "You caught Blue!" and running out of moves shows "Blue got away!"; Try again / Play again restarts with the same options, a fresh scramble, and a bank that keeps rotating; Main Menu returns to Game Select; `game_setup.py` is pygame-free with a guard test proving it; `pytest` passes with the new `test_game_setup.py` suite; and the work is committed.
