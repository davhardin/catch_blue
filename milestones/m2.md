# M2 — Movement: the player walks, Blue runs

Breakdown of M2 from `implementation_plan.md` §5 (est. 4–6 hours total).

M1 ended with a board you can only look at — on purpose. M2 makes it react: clicking a square next to the player moves the player there, and Blue takes one greedy step away when told to. **No questions yet.** M3 wedges the quiz between "click" and "move"; M2's job is to make the movement rules *exist*, be *visible*, and be *tested*. Because nothing triggers a flee naturally until wrong answers exist, M2 uses a debug key as a stand-in.

## Decisions made

- **Adjacency is 4-way orthogonal** *(decided 2026-08-25)*. Every character — Player, Blue, and later Red — moves only left, right, up, or down, one square at a time, within the board. Manhattan distance (`abs(dc) + abs(dr)`) is the matching metric; `is_adjacent` checks it equals exactly 1. Turn semantics are settled too: the player moves only on a *correct* answer, Blue only on an *incorrect* one — recorded in `implementation_plan.md` §4 (Red's trigger is deliberately still open there, pending balance work). That gate is M3's to build; M2 movement stays unconditional scaffolding.
- **Rules are queryable, and there is one source of truth.** `legal_moves(...)` returns the set of cells a character may step to. That same set drives *both* the on-screen highlight and the click validation — the UI literally shows what the rule function returns, so they can never disagree. `move_to(cell)` is a dumb setter that just updates `self.cell`; legality is the *caller's* question, asked through `legal_moves` before calling it. Don't validate in both places — two gates drift apart.
- **The metric and the adjacency rule live side by side.** `is_adjacent(a, b)` and `distance(a, b)` sit next to each other in `board.py` as free functions (they're properties of two cells, not of any particular board — no `self` needed). Blue's flee uses `distance`; movement uses `is_adjacent`. Keeping them adjacent in the file is what keeps them consistent: if one goes 8-way, the other goes with it.
- **The base class earns its first behavior.** m1.md said no behavior on `Character` until M2 demands it. M2 demands it: `move_to` and `legal_moves` go on `Character` because both subclasses need them (Player to move, Blue to enumerate flee candidates). `flee_step` is Blue's alone — the first real divergence, right where the m1 decision predicted it.
- **Occupancy is an explicit argument, not board state.** "Can't move onto an occupied square" is handled by passing a set of blocked cells into `legal_moves` (for the player: `{blue.cell}`; for Blue: `{player.cell}`). No occupancy registry on `Board` — with two entities, a set literal at the call site is honest and testable; revisit if Red makes three.
- **Blue flees greedily and deterministically.** Candidates are Blue's legal moves; pick the one that *strictly* increases `distance` to the player, else stay put. Iterate candidates in sorted order so ties break the same way every run — that's what makes flee behavior assertable in a test. Greedy is enough: Blue only flees on wrong answers, so the chase is won by answering correctly (Blue freezes), not by outsmarting a pathfinder.
- **The flee trigger is a debug key.** A key press (say `F`) makes Blue take one flee step, standing in for "wrong answer" until M3 exists. Scaffolding — it gets deleted when the question flow lands.
- **Catching is a `print` for now.** Clicking Blue's cell while adjacent prints something like `caught!` — the win screen is M4's. Same discipline as M1's `print(cell)`: prove the detection, defer the consequence.

### M2.e — Blue flees (~75 min)
- [x] `Blue.flee_step(board, threat)` → the `Cell` Blue should move to: its legal moves (blocked = `{threat}`), keeping only cells that *strictly* increase `distance` to `threat`; best one wins, sorted order breaks ties; nowhere better → current cell
- [x] Caller applies it: `blue.move_to(blue.flee_step(board, player.cell))` — the chooser stays a pure, testable function
- [x] Debug key in `main.py` (e.g. `F` on `KEYDOWN`) fires one flee step

**Success check:** stand next to Blue and press `F` — Blue steps directly away; chase it to an edge and it runs along the edge, never off it, never onto you.

*Correction (2026-08-26, discovered writing M2.f's tests):* the "strict vs `>=`" knob is wired to nothing. Every orthogonal step flips Manhattan-distance parity — `get_distance` changes by exactly ±1, never 0 — so an equal-distance candidate cannot exist and `>` and `>=` produce identical behavior. The knob that *does* exist is the tie-break among equally-good improving candidates (currently deterministic sorted order); randomizing it would make Blue less predictable. Logged under playtesting considerations in `implementation_plan.md` §7.

## Traps

1. **Metric drift.** Adjacency 4-way but distance Chebyshev (or vice versa) gives Blue weird diagonal-flavored judgment. The two functions sit together in `board.py` precisely so a change to one stares at the other.
2. **`max()` ties are decided by iteration order.** Two flee candidates at equal distance → whichever came first wins, and `set` iteration order isn't something to build behavior on. Sort the candidates before choosing; the determinism is what makes M2.f's flee tests possible.
3. **Filter, then choose.** Drop off-board and blocked cells from Blue's candidates *before* maximizing distance. Choose-then-filter lets "the best cell" be the player's own square.
4. **Selection semantics just changed under you.** In M1 every board click selected; now adjacent clicks move instead. Decide deliberately what a selection *is* now — likely answer: it stays for non-legal squares today and becomes "the square whose question you're answering" in M3. Whatever you pick, make the click handler read as one clean decision ladder: catch → move → select.
5. **`if cell:` strikes again.** Legal-move sets contain `Cell(0, 0)`, which is falsy as a tuple. Membership checks (`in`) are safe; truthiness checks are not. Same trap as M1, new costume.
6. **Don't build the turn engine.** No turn counter, no state machine, no "Blue's turn" phase — one debug key and direct function calls are the whole orchestration until M3/M4 give the game a real rhythm.

## Done when

Clicking an adjacent square moves the player there and the legal squares are visibly marked; non-adjacent clicks don't move; clicking Blue while adjacent prints the catch; the debug key sends Blue one greedy step away — never off the board, never onto the player, pinned when cornered; `pytest` passes including the new movement and flee tests; and the work is committed.
