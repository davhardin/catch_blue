# M1 — Clicks land on squares; Player and Blue on the board

Breakdown of M1 from `implementation_plan.md` §5 (est. 3–5 hours total).

M0 proved the grid math in tests. M1 proves it against a real mouse, and puts two things on the board to look at. **Nothing moves yet** — movement rules are M2, and a click's only job here is to report which square it hit.

## Decisions made

- **`characters.py` stays pygame-free.** Same line as `board.py`: a `Player` knows it is at `Cell(0, 4)`, and knows nothing about pixels. Drawing goes through `BoardView.cell_to_rect`, which already exists. This keeps starting-position and (in M2) movement rules unit-testable.
- **No `NPC` base class yet.** `implementation_plan.md` §4 plans `NPC` → `Blue`, `Red`. Build `Player` and `Blue` as plain classes now and extract the base when Red actually arrives in Phase 2. A one-subclass hierarchy teaches you nothing and guesses at an interface you can't see yet.
- **Click handling lives in `main.py` for now.** It belongs in `BoardState` once the state machine exists (M4). Putting it in the loop today is not debt as long as it stays five lines — resist growing an `if`-ladder there.

| File | Owns |
|---|---|
| `characters.py` (no `import pygame`) | `Player.cell`, `Blue.cell`; later `move_to`, flee logic |
| `BoardView` | drawing entities — reuses `cell_to_rect`, plus hover/selection highlights |
| `main.py` | translating mouse events into cells, holding "what's selected" |

## Sub-goals

### M1.a — Mouse click → cell (~30 min)
- [x] Handle `MOUSEBUTTONDOWN` in the event loop
- [x] Guard on `event.button == 1` so right-clicks don't count
- [x] `cell = view.pixel_to_cell(*event.pos)`, `print(cell)` for now
- [x] Handle the `None` case explicitly — clicks off the board are normal, not errors

**Success check:** clicking each of the four corner squares prints `(0,0)`, `(4,0)`, `(0,4)`, `(4,4)`; clicking the margin prints nothing.

This is the first real test of `pixel_to_cell`. The unit tests fed it numbers you computed; now the OS is feeding it numbers, and if the two disagree you want to know before anything depends on it.

### M1.b — Hover highlight (~30 min)
- [x] Track the cell under the cursor (`MOUSEMOTION`, or `pygame.mouse.get_pos()` once per frame)
- [x] Draw a brighter fill or thicker border on that cell
- [x] Store it as `Cell | None` on the view or in `main.py` — not as a flag on each cell

**Success check:** the highlight follows the mouse exactly, with no lag and no off-by-one at square boundaries.

Worth doing before entities, not after. It turns `pixel_to_cell` into something you can *see* being right or wrong across the whole board in two seconds of mouse movement — a far better check than clicking 25 squares by hand. It's also the groundwork for M2's "show me my legal moves."

### M1.c — `Player` and `Blue` (~45 min)
- [ ] `characters.py` with both classes, each holding a `Cell`
- [ ] Starting positions derived from board size, not hardcoded to 5×5
- [ ] Player bottom-left `Cell(0, rows - 1)`, Blue top-right `Cell(cols - 1, 0)`

**Success check:** `pytest` confirms the two start on opposite corners for a 5×5 *and* a 9×9 board.

Deriving from `board.cols` / `board.rows` costs one line now and is the difference between Run from Red working and needing a rewrite. Remember row 0 is the **top** row on screen.

### M1.d — Draw them (~45 min)
- [ ] A draw call per entity, positioned via `view.cell_to_rect(entity.cell)`
- [ ] Inset the shape inside the cell so the grid line stays visible — `rect.inflate(-12, -12)`, or a circle at `rect.center`
- [ ] Colors in `constants.py`, distinguishable without relying on hue alone

**Success check:** two clearly different markers sit in opposite corners and stay put when you switch `Board(5, 5)` to `Board(9, 9)`.

Colored circles are fine. Sprites are M6 polish, and a placeholder you can see is worth more right now than art you'll redraw later.

## Traps

1. **Check `event.button`.** Without it, right-click and middle-click also select. `MOUSEBUTTONDOWN` fires for all of them, and scroll wheel events show up here too on some setups.
2. **`pixel_to_cell` returns `None` constantly** — every click in the 40px margin, every click in the HUD column. Treat it as the ordinary case, not an error path. `if cell is not None:`, never `if cell:`.
3. **Draw order matters.** Grid first, then hover highlight, then entities, then selection. Anything drawn earlier gets painted over — if Blue vanishes, this is why.
4. **Mouse coordinates and `pygame.SCALED`.** The window is created with `SCALED`, so pygame maps mouse input back into 1280×720 logical space. If the hover highlight is ever offset from the real cursor — most likely after resizing or going fullscreen — suspect this first, and prefer `event.pos` from the event over polling `pygame.mouse.get_pos()`, since the event carries the position that belonged to that click.
5. **Don't let anything move.** The temptation at M1.e is to make a click move the player, because it's four lines away. That's M2, and it needs adjacency rules that don't exist yet. Ending M1 with a board you can only *look at* is the correct outcome.
6. **Two entities, one cell** isn't possible yet with fixed corners, but it's the first question M2 has to answer. Note it and move on.

## Done when

Hovering highlights the correct square anywhere on the board, left-clicking selects it, clicks outside the grid do nothing, Player and Blue sit in opposite corners, `pytest` passes, and the work is committed.
