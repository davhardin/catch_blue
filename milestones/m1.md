# M1 — Clicks land on squares; Player and Blue on the board

Breakdown of M1 from `implementation_plan.md` §5 (est. 3–5 hours total).

M0 proved the grid math in tests. M1 proves it against a real mouse, and puts two things on the board to look at. **Nothing moves yet** — movement rules are M2, and a click's only job here is to report which square it hit.

## Decisions made

- **`characters.py` stays pygame-free.** Same line as `board.py`: a `Player` knows it is at `Cell(0, 4)`, and knows nothing about pixels. A character's `shape` is a plain string name (`"circle"`, `"square"`) and its `color` a plain `(r, g, b)` tuple from `constants.py`; `BoardView` translates name → pixels by dispatching on `entity.shape`. This keeps starting-position and (in M2) movement rules unit-testable, and the guard test passing.
- **`Character` base class** *(revised 2026-08-25 — supersedes "no `NPC` base class yet")*. The original plan deferred any hierarchy until Red arrived, because a one-subclass hierarchy guesses at an interface you can't see. With `Player` and `Blue` both in hand the shared interface is visible — a cell, a shape, a color — so the base is extracted from evidence, not speculation. `Character` holds exactly those three things and nothing else: `__init__(self, cell)`, plus `shape` and `color` as **class attributes** (defaults: `"circle"`, neutral color). Subclasses override in the class body (`Blue` sets `shape = "square"`); a single instance can shadow either with `self.shape = ...`. No behavior (`move_to`, turn logic) goes in the base until M2 demands it — the Red/flee question still shapes any behavioral hierarchy.
- **Off-board clicks clear the selection** *(decided in code, M1.e)*. The click handler stores `pixel_to_cell`'s result unconditionally, so a click in the margin sets `selected = None` — clear-on-miss rather than ignore-on-miss. Standard UI behavior, and one line simpler; revisit if M2's move-selection flow wants misses ignored.
- **Starting positions live in `at_start` classmethods.** `__init__(self, cell)` takes any cell, so alternate placements stay easy. The corner rule — derived from board size, never hardcoded — lives in a per-subclass classmethod `at_start(cls, board)` returning `cls(Cell(...))`. That gives the rule a home pytest can reach, instead of burying it in `main.py`.
- **Click handling lives in `main.py` for now.** It belongs in `BoardState` once the state machine exists (M4). Putting it in the loop today is not debt as long as it stays five lines — resist growing an `if`-ladder there.

| File | Owns |
|---|---|
| `characters.py` (no `import pygame`) | `Character` base (cell; `shape`/`color` class-attribute defaults); `Player`, `Blue` subclasses; `at_start` constructors; later `move_to`, flee logic |
| `BoardView` | drawing entities — dispatches on `entity.shape`, reuses `cell_to_rect`, plus hover/selection highlights |
| `main.py` | translating mouse events into cells, holding "what's selected" |

## Traps

1. **Check `event.button`.** Without it, right-click and middle-click also select. `MOUSEBUTTONDOWN` fires for all of them, and scroll wheel events show up here too on some setups.
2. **`pixel_to_cell` returns `None` constantly** — every click in the 40px margin, every click in the HUD column. Treat it as the ordinary case, not an error path. `if cell is not None:`, never `if cell:`.
3. **Draw order matters.** Grid first, then hover highlight, then entities, then selection. Anything drawn earlier gets painted over — if Blue vanishes, this is why.
4. **Mouse coordinates and `pygame.SCALED`.** The window is created with `SCALED`, so pygame maps mouse input back into 1280×720 logical space. If the hover highlight is ever offset from the real cursor — most likely after resizing or going fullscreen — suspect this first, and prefer `event.pos` from the event over polling `pygame.mouse.get_pos()`, since the event carries the position that belonged to that click.
5. **Don't let anything move.** The temptation at M1.e is to make a click move the player, because it's four lines away. That's M2, and it needs adjacency rules that don't exist yet. Ending M1 with a board you can only *look at* is the correct outcome.
6. **Two entities, one cell** isn't possible yet with fixed corners, but it's the first question M2 has to answer. Note it and move on.
7. **Don't let pygame creep into `Character`.** Once a base class exists, the pull is a `draw(self, screen)` method on the entity — which imports pygame into `characters.py` and breaks the guard test. Entities say *what* they are (`shape`, `color`); `BoardView` decides how that looks.

## Done when

Hovering highlights the correct square anywhere on the board, left-clicking selects it, clicks outside the grid clear the selection, Player and Blue sit in opposite corners, `pytest` passes, and the work is committed.
