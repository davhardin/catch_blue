# M8 — Run from Red

Breakdown of the first Phase 2 mode from `implementation_plan.md` §5 (plan estimate +8–15 build hours; the sub-goals below add to roughly 9–12, with the accent comparison the widest range). Written 2026-09-20 at the close of the pre-Phase-2 refactor.

**Where this starts.** Steps 1–4 of `claude_refactor_suggestions.md` §13 landed on 2026-09-20, each verified against the M7 galleries byte for byte: a pygame-free `Match` that owns turn accounting; `QuestionPopup` and `CellTopics` extracted from the play state; `Board.distance` and catches through `board.neighbors`; one shared step-chooser (`best_step`) proven equal to Blue's old flee over 47,160 seeded cases; and a mode registry (`modes.py`) with a `Rules` protocol (`rules.py`) that the play state consults at every point where Catch Blue's rules used to be inline. The test suite was re-swept to the new surface at the end of step 4. M8 is step 5: the first mode built *on* those seams, and the proof that they hold.

**What M8 is.** A `Red` character and a `RunFromRedRules` class; a registry entry with its own preset table, which is what makes the Game Select button live and puts a Game row on the Settings screen; end-screen copy; a headless play-through; and the per-mode accent — built two ways side by side so the looks can be compared and one deleted. Two small items carried in from the step 4 review ride along: the Settings screen's fifth row overflows on the pixel theme, and the registry's `npc_color_role` field has no reader.

**Order of work: rules before screen, again.** Red and its rules are pure and testable with a board, two characters, and a seeded `Random`; they come first and are done before any screen changes. The registry entry activates the mode in the menus in one change. The accent is last and is the only part that touches the renderer.

**Budget, honestly.** M8.a–c reuse everything: the popup, the reveal, pause, the end screen, the board view, the tier policy, the pool cycling. If any of those needs a change for Red, that is a finding about the step 4 seams, not a Red feature — write it down in the refactor doc's §2a before working around it. M8.d is the open-ended part; its budget is bounded by the decision at its end.

## Decisions made

- **A rules object, not a flag and not a sibling state** *(refactor doc §2, 2026-09-20)*. `PlayState` is generic; Run from Red is `RunFromRedRules` in `rules.py` plus a registry entry in `modes.py`. Nothing in `states/` changes for the mode itself.
- **Red steps toward the Player on incorrect answers only** *(GDD §2–3, David, 2026-09-20)*. Correct answers move the Player to the clicked square; Red holds still. This mirrors Blue with the comparison flipped: `best_step(..., prefer=lt, ...)`.
- **Red catches by landing on the Player's square** *(David, 2026-09-20)*. So Red's chooser is called with an empty blocked set — the Player's cell is a legal destination for Red. The catch is detected in `on_incorrect` (Red's cell equals the Player's after the step) and returned as an immediate `Outcome.LOSE`, so the shared move deduction still runs and the end screen draws the catching frame. `entities()` returns `[player, red]` so Red draws above the Player on that frame.
- **The Player is blocked from Red's cell** *(default from refactor doc §14; David to confirm or reverse in M8.a)*. Red landing on the Player does not imply the reverse; a Player who could step onto Red would have no reason to, and the click would need an intent that does not exist. `player_blocked` returns `{red.cell}`; `click_intent` returns `MOVE` or `None`, never `CATCH`.
- **Starts: Player center, Red in the bottom-left corner** *(GDD; the corner is the mirror of Catch Blue's Player start, so the two modes share their starting distance on a given board)*. `start_cells` returns `(Cell(cols // 2, rows // 2), Cell(0, rows - 1))`.
- **Win and loss.** Loss is the catch. Win is the mirror of Catch Blue's early loss: after each turn, `moves_remaining < board.distance(player, red)` means Red cannot close even if every remaining answer is wrong, so the Player has escaped. Running out of moves without a catch is the same rule (zero is less than any positive distance). `moves_remaining == distance` is *not* a win: exactly that many wrong answers would still be a catch.
- **The question comes from the clicked square** *(default; refactor doc §14 lists it as open)*. The Player picks a subtopic by picking a square, the same mental model as Catch Blue; asking Red's square instead would make the board's labels advisory. `question_cell` returns the target. If playtesting says the fled-to square is too easy to game, this is one method to change.
- **Pressure distance is Player-to-Red.** So the distance tier policy asks tier 3 when Red is adjacent and tiers 1–2 when Red is far, which is the right pressure curve for a chase: the hard question is the one that decides whether you get caught.
- **Presets are Red's own table, David's numbers** *(refactor doc §8b)*. The arithmetic to tune against, on a 9×9 with the starts above: starting distance 8; a wrong answer costs a move and closes the distance by one, leaving `moves − distance` unchanged; a correct answer that steps *away* costs a move and opens the distance by one, closing that gap by two. With 15 moves the gap starts at 7 and the Player wins after four fleeing correct answers, while a catch needs eight wrong answers before that — a forgiving game. Longer move limits make the escape longer, not harder; a smaller board (7×7, start distance 6) makes Red's catch quicker. The rule stays; the table is the knob. Starting points to playtest: **easy** 7×7 / 20 / tiers 1+2; **medium** 9×9 / 25 / distance; **hard** 9×9 / 30 / distance.
- **Board size is a Red setting too**, with the same 5/7/9 labels — those labels are honest for a square grid, which is what Run from Red is (refactor doc §8b's objection was to reinterpreting them for strips and mazes).
- **Accent: both mechanisms, side by side** *(David, 2026-09-20; refactor doc §2b, §11, §11a, §14)*. The registry's `accent` is a key. `Game.renderer_for(accent)` resolves it to a `Theme` and caches a `Renderer` per accent; `start_play` picks the mode's. Two resolvers are built: a hue remap of `PIXEL`'s blue-grey roles (plan §7), and a whole-skin variant from the Pixel UI pack (§11a). The gallery renders one board per accent per mechanism; at the end of M8 one ships and the other is deleted, and plan §7, the GDD, and `assets/ATTRIBUTION.md` are updated to the winner.
- **`npc_color_role` leaves the registry** *(step 4 review)*. `Red.color_role = 'red'` on the class is the single source of truth, as `Blue.color_role` already is; `make_npc` returns the class and the view reads the role from the entity. If a later mode needs the registry to pick a color, add it back with a reader.
- **Red is a square** — NPCs are squares, the Player is a circle, until sprites (M7.g) replace shapes.
- **Out of scope:** the camera, Race Green, Find Yellow, sprites, sound, persistence. Any change to `board.py` beyond what exists.

## Traps

1. **Blocking Red from the Player's cell.** The one-argument-left-out rule: Red's chooser must get an *empty* blocked set, or Red can never catch. Test it directly — Red adjacent to the Player, wrong answer, Red on the Player's cell.
2. **Detecting the catch in the wrong place.** The catch is `on_incorrect`'s immediate result, before the shared deduction, exactly as Catch Blue's catch-win is `on_correct`'s. Detecting it in `outcome` would also work today, but `outcome` runs after the deduction and would let a "moves < distance" check race it; keep the handler as the source.
3. **The draw order on the catching frame.** `entities()` order is the draw order. Red last. The end screen draws the play state beneath its panel, so that frame is what the student sees for as long as they like.
4. **`state.blue` in tests and the gallery.** The shim raises for any NPC that is not Blue. Everything that means "the NPC" says `npc`; only tests *about Blue* say `blue`.
5. **The tier policy reads the wrong distance.** `pressure_distance` is Player-to-Red; the Topics screen's eligibility check uses Red's starting distance, not Blue's. A wrong start cell here shows up as Start greyed out for a preset that should work.
6. **The Settings fifth row on pixel.** Measured: 781 px bottom against the 756 px Back line, no horizontal overlap, inside the screen. It is a layout test's job to keep it that way after the fix, on both themes.
7. **Balance by rule instead of by knob.** If the escape is too easy, the temptation is to make Red move every turn. That is a different game (plan §7 recorded the choice). Tune the move limit and board size first; if the rule has to change, it changes in the GDD first.
8. **The accent comparison never ending.** M8.d has a decision at its end and the loser is deleted. Two live mechanisms is a maintenance cost the project does not want.
9. **Red's color against a red board.** The Okabe-Ito vermillion (213, 94, 0) on a red-shifted cell may not clear the contrast ratio. The character roles are palette values; if one has to move for one mode, that is a per-accent palette entry, not a special case in the renderer.
