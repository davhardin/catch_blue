# M8 — Run from Red

Breakdown of the first Phase 2 mode from `implementation_plan.md` §5 (plan estimate +8–15 build hours; the sub-goals below add to roughly 11–14, with the accent comparison the widest range). Written 2026-09-20 at the close of the pre-Phase-2 refactor; M8.e, the Select Topics scroll bar, was added on 2026-09-30, and the sweep that had been M8.e became M8.f.

**Where this starts.** Steps 1–4 of `claude_refactor_suggestions.md` §13 landed on 2026-09-20, each verified against the M7 galleries byte for byte: a pygame-free `Match` that owns turn accounting; `QuestionPopup` and `CellTopics` extracted from the play state; `Board.distance` and catches through `board.neighbors`; one shared step-chooser (`best_step`) proven equal to Blue's old flee over 47,160 seeded cases; and a mode registry (`modes.py`) with a `Rules` protocol (`rules.py`) that the play state consults at every point where Catch Blue's rules used to be inline. The test suite was re-swept to the new surface at the end of step 4. M8 is step 5: the first mode built *on* those seams, and the proof that they hold.

**What M8 is.** A `Red` character and a `RunFromRedRules` class; a registry entry with its own preset table, which is what makes the Game Select button live and puts a Game row on the Settings screen; end-screen copy; a headless play-through; and the per-mode accent — built two ways side by side so the looks can be compared and one deleted. Two small items carried in from the step 4 review ride along: the Settings screen's fifth row overflows on the pixel theme, and the registry's `npc_color_role` field has no reader. One item came from a playtest: a student playing the Pages build on an iPad could not scroll the Select Topics list, because taps arrive as clicks but nothing on a touch screen sends a mouse wheel. M8.e gives that list a scroll bar.

**Order of work: rules before screen, again.** Red and its rules are pure and testable with a board, two characters, and a seeded `Random`; they come first and are done before any screen changes. The registry entry activates the mode in the menus in one change. The accent is the only Red work that touches the renderer. The scroll bar touches only the menus and does not depend on Red or the accent, so it can land at any point before M8.f's sweep.

**Budget, honestly.** M8.a–c reuse everything: the popup, the reveal, pause, the end screen, the board view, the tier policy, the pool cycling. If any of those needs a change for Red, that is a finding about the step 4 seams, not a Red feature — write it down in the refactor doc's §2a before working around it. M8.d is the open-ended part; its budget is bounded by the decision at its end.

**Status (2026-09-30).** M8.a and M8.b are implemented and reviewed. M8.c's play-through was driven headlessly from the real menus on both themes and passes (the script and frames are machine-local, in `catch_blue_local_only/m8c_check/`). One seam changed on the way: the `Rules` protocol gained `allowed_tiers` and `wanted_tier` for Red's inverted tier curve, now logged in the refactor doc's §2a. **Every test item in M8 is held for one sweep in M8.f**, which also carries the trim from the 2026-09-30 suite audit *(David, 2026-09-30)*. One existing test went stale with M8.b: `tests/test_lift.py::test_menu_buttons_pop_on_hover_and_inactive_never_lift` uses Run from Red as its inactive button, and no inactive mode remains (it fails on pixel; suite 566/567). Its fix is in M8.f. M8.e (the scroll bar) was added on 2026-09-30 after the iPad playtest and is not started; the sweep that was M8.e is now M8.f.

## Decisions made

- **A rules object, not a flag and not a sibling state** *(refactor doc §2, 2026-09-20)*. `PlayState` is generic; Run from Red is `RunFromRedRules` in `rules.py` plus a registry entry in `modes.py`. Nothing in `states/` changes for the mode itself.
- **Red steps toward the Player on incorrect answers only** *(GDD §2–3, David, 2026-09-20)*. Correct answers move the Player to the clicked square; Red holds still. This mirrors Blue with the comparison flipped: `best_step(..., prefer=lt, ...)`.
- **Red catches by landing on the Player's square** *(David, 2026-09-20)*. So Red's chooser is called with an empty blocked set — the Player's cell is a legal destination for Red. The catch is detected in `on_incorrect` (Red's cell equals the Player's after the step) and returned as an immediate `Outcome.LOSE`, so the shared move deduction still runs and the end screen draws the catching frame. `entities()` returns `[player, red]` so Red draws above the Player on that frame. Red's square is larger than the Player's circle, so on that frame the Player is hidden entirely and the student sees only Red. That is accepted for now *(David, 2026-09-30)*; the animation pass (M9 or M10) can revisit it.
- **The Player is blocked from Red's cell** *(refactor doc §14's default, confirmed by David 2026-09-23)*. Red landing on the Player does not imply the reverse; a Player who could step onto Red would have no reason to, and the click would need an intent that does not exist. `player_blocked` returns `{red.cell}`; `click_intent` returns `MOVE` or `None`, never `CATCH`.
- **Starts: Player center, Red in the bottom-left corner** *(GDD; the corner is the mirror of Catch Blue's Player start, so the two modes share their starting distance on a given board)*. `start_cells` returns `(Cell(cols // 2, rows // 2), Cell(0, rows - 1))`.
- **Win and loss.** Loss is the catch. Win is the mirror of Catch Blue's early loss: after each turn, `moves_remaining < board.distance(player, red)` means Red cannot close even if every remaining answer is wrong, so the Player has escaped. Running out of moves without a catch is the same rule (zero is less than any positive distance). `moves_remaining == distance` is *not* a win: exactly that many wrong answers would still be a catch.
- **The question comes from the clicked square** *(confirmed by David 2026-09-23; refactor doc §14 still lists it as open until M8.f)*. The Player picks a subtopic by picking a square, the same mental model as Catch Blue; asking Red's square instead would make the board's labels advisory. `question_cell` returns the target. If playtesting says the fled-to square is too easy to game, this is one method to change.
- **Pressure distance is Player-to-Red, and Red's tier curve runs the other way from Catch Blue's** *(David, 2026-09-30)*. Under "Distance based", Red prefers tier 3 at three or more squares, tier 2 at two, and tier 1 when adjacent, and every tier stays eligible at every distance: distance sets the preferred tier, not which tiers are allowed, so the bank can fall back freely when a tier runs thin. The reasoning: the questions that decide a Run from Red game are the fleeing correct answers that win it, so the hard ones come at range, where they push back against a runaway lead, while Red's chase supplies the pressure up close. Every Red start is three or more squares away (4, 6, 8 on 5/7/9), so a distance-based game opens on tier 3 and eases only when Red is within two squares. That is the intent. A curve that climbs gradually with distance would need thresholds scaled to the board. The curve lives in `RunFromRedRules.allowed_tiers` and `wanted_tier`, two methods added to the `Rules` protocol for it (refactor doc §2a); Catch Blue's versions delegate to `game_setup`'s functions unchanged.
- **Presets are Red's own table, David's numbers** *(refactor doc §8b; kept after the 2026-09-30 balance simulation)*: **easy** 7×7 / 15 / T1 + T2; **medium** 7×7 / 20 / distance; **hard** 5×5 / 25 / distance. The arithmetic: the starting distance is 4, 6, or 8 on 5/7/9. A wrong answer costs a move and closes the distance by one, so `moves − distance` is unchanged. A correct answer that steps *away* costs a move and opens the distance by one, which closes that gap by two. On an open grid the Player therefore wins after ⌊gap / 2⌋ + 1 fleeing correct answers (five on easy). The board's walls change that. A runner who reaches a corner cannot step away, and Red traps them there, so on a bounded board **a longer move limit is harder, not just longer, and a bigger board is easier**, because it gives more room to run. Hard's escape takes 18 correct answers even with no wrong ones, not the open-grid 11. Simulated win rates, with 4,000 games per cell, the Player always fleeing, and every answer equally likely to be right (tiers not modeled):

  | Win % at 50% / 60% accuracy | easy | medium | hard |
  |---|---|---|---|
  | Run from Red | 88 / 96 | 73 / 92 | 27 / 57 |
  | Catch Blue | 32 / 60 | 32 / 60 | 18 / 48 |

  Red's easy and medium are far kinder than Catch Blue's easy. Red's medium and hard play harder than these numbers, because the inverted curve asks mostly tier 3. The rule stays; the table is the knob (Trap 7).
- **Board size is a Red setting too**, with the same 5/7/9 labels — those labels are honest for a square grid, which is what Run from Red is (refactor doc §8b's objection was to reinterpreting them for strips and mazes).
- **Accent: both mechanisms, side by side** *(David, 2026-09-20; refactor doc §2b, §11, §11a, §14)*. The registry's `accent` is a key. `Game.renderer_for(accent)` resolves it to a `Theme` and caches a `Renderer` per accent; `start_play` picks the mode's. Two resolvers are built: a hue remap of `PIXEL`'s blue-grey roles (plan §7), and a whole-skin variant from the Pixel UI pack (§11a). The gallery renders one board per accent per mechanism; at the end of M8 one ships and the other is deleted, and plan §7, the GDD, and `assets/ATTRIBUTION.md` are updated to the winner.
- **`npc_color_role` leaves the registry** *(step 4 review)*. `Red.color_role = 'red'` on the class is the single source of truth, as `Blue.color_role` already is; `make_npc` returns the class and the view reads the role from the entity. If a later mode needs the registry to pick a color, add it back with a reader.
- **Red is a square** — NPCs are squares, the Player is a circle, until sprites (M7.g) replace shapes.
- **Out of scope:** the camera, Race Green, Find Yellow, sprites, sound, persistence. Any change to `board.py` beyond what exists.

### M8.e — A scroll bar for Select Topics (~2 h)

From a playtest on 2026-09-30: a student played the Pages build on an iPad. Taps arrive as clicks, so every button and checkbox works, but the topics list scrolls only by mouse wheel (the `MOUSEWHEEL` branch in `TopicsState.handle_events`), and a touch screen never sends a wheel event. A&P's list has 21 rows (All plus 20 topics) and shows 9 at a time, so 12 rows can't be reached on a tablet. The fix is a scroll bar beside the list, with parts you can tap. Dragging the thumb is a bonus on touch screens.

Measured on 2026-09-30: the list's clip region runs from y 260 to 728, and `max_scroll` is 624 px (12 rows). Its right edge is at 1081 px on flat and 1192 px on pixel, because the widest label widens the instance's `scroll_region` past the module's `SCROLL_REGION` (Trap 10). The screen is 1600 px wide, so both themes have room for the bar.

**Defaults** (David confirms or reverses):

- **Placement.** Just right of the instance `scroll_region`, with the same top and bottom as the list, so the bar's length matches what it scrolls.
- **What each part does.** The up and down arrows move one row, like one wheel notch. A tap on the track above or below the thumb moves one page: the visible rows less one (8), so the edge row stays in view for context. Dragging the thumb sets the offset in proportion to where it is. All three go through `_set_scroll_offset`, so they snap to whole rows and clamp just like the wheel.
- **Thumb size and position.** Length = track length × visible rows ÷ total rows (9/21 for A&P), with a minimum so the thumb stays easy to grab. Top = track top + (offset ÷ `max_scroll`) × (track length − thumb length). When the list fits (`max_scroll == 0`), there is no bar: nothing is drawn and nothing is hit-tested.
- **Sized for a finger.** A landscape iPad shows the 1600 px canvas in 1024–1180 CSS px, a scale of 0.64–0.74, so Apple's 44 pt minimum touch target works out to about 60–70 game px. Make the bar about 64–72 px wide and the arrows about as tall. The list's 52 px rows come out at about 33–38 pt and still work, but a full-width row is a far easier target than a narrow bar. Portrait shrinks the canvas further. The game is landscape-first, so portrait isn't a sizing target.
- **Look.** One new renderer primitive that draws through the theme like `button` and `panel` do: the track as a panel or an inactive button, and the thumb and arrows as buttons. That way pixel gets its nine-slice and flat gets its plain fill. Draw the arrows as triangles so they don't depend on the font having ▲ and ▼.
- **Input.** Handle mouse events only (Trap 12). A button-down on the thumb starts a drag and records where on the thumb it was grabbed. `MOUSEMOTION` moves the thumb while it is held, and the button-up ends the drag wherever the pointer is. The bar is checked before the list's hit test, and it lies outside `scroll_region`, so a tap on the bar never toggles a checkbox.
- **Out of scope.** Swiping the list itself (Trap 11), auto-repeat while an arrow is held, and scroll bars on other screens (Select Topics is the only one that scrolls).

**Checklist:**

- [ ] David confirms or reverses the defaults above
- [ ] `ScrollBar` in `ui.py`: built from the list's region, row height, visible rows, and row count. It gives the arrow, track, and thumb rects for the current offset, plus a hit test that names the part under a point. Pure rect math, no drawing state.
- [ ] The renderer's scroll-bar primitive on both themes. On pixel, it uses the skin's existing elements unless the bar needs one of its own.
- [ ] `TopicsState` owns the bar, routes button-down, motion, and button-up to it before the list's hit test, and draws it after the list's clip. The wheel branch stays as it is.
- [ ] Headless check on both themes: frames at the top, middle, and bottom offsets; synthetic taps on each arrow and on each side of the thumb; a thumb drag from top to bottom reaches `max_scroll`; the same sequence with `touch=True` on the events gives the same result
- [ ] On a touch screen: Chrome DevTools' device toolbar (an iPad with touch emulation) on a local `pygbag` build, then a real iPad once the Pages site has the bar. Only Safari on the device shows whether a finger drag on the canvas gets taken as a page gesture. The build's `index.html` sets no `touch-action` on the canvas; whether pygbag's loader script sets one hasn't been checked. If Safari does take the drag, the arrows and track still work by tap, so a broken drag is a note for later, not a blocker.
- [ ] **Ship now or with M8 (David).** A push to `main` deploys whatever is committed, and M8.a–c's uncommitted work includes `constants.py`, which the bar touches too. To get the bar to students before M8 closes, either commit only the bar's hunks, or commit M8.a–c along with it, which also puts Run from Red live on the site before its accent exists.
- [ ] Tests *(held for M8.f's sweep, like the rest of M8's)*: the thumb sits at the top at offset 0, flush with the bottom at `max_scroll`, and has the expected length for A&P's 21 rows; each arrow moves one row and clamps at both ends; a track tap moves a page and clamps; a drag snaps to rows and ends on a button-up outside the bar; `touch=True` events behave like mouse events; with `max_scroll` at 0 there is no bar and no hit; a tap on the bar never toggles a checkbox. `test_menu_layout.py::test_topics_screen_regions_do_not_collide` and `test_pixel_layout.py::test_menus_end_controls_titles_hud_and_scroll` grow to cover the bar on both themes: inside the screen, right of the instance `scroll_region`, clear of Start, Back, and the title.

## Traps

1. **Blocking Red from the Player's cell.** The one-argument-left-out rule: Red's chooser must get an *empty* blocked set, or Red can never catch. Test it directly — Red adjacent to the Player, wrong answer, Red on the Player's cell.
2. **Detecting the catch in the wrong place.** The catch is `on_incorrect`'s immediate result, before the shared deduction, exactly as Catch Blue's catch-win is `on_correct`'s. Detecting it in `outcome` would also work today, but `outcome` runs after the deduction and would let a "moves < distance" check race it; keep the handler as the source.
3. **The draw order on the catching frame.** `entities()` order is the draw order. Red last. The end screen draws the play state beneath its panel, so that frame is what the student sees for as long as they like.
4. **`state.blue` in tests and the gallery.** The shim raises for any NPC that is not Blue. Everything that means "the NPC" says `npc`; only tests *about Blue* say `blue`.
5. **The tier policy reads the wrong distance, or the wrong curve.** `pressure_distance` is Player-to-Red, and Red's curve is its own (`allowed_tiers` / `wanted_tier` on `RunFromRedRules`), not `game_setup`'s functions. Red's eligibility does not depend on distance today, so its `menu_eligible` cannot grey out Start by a wrong start cell; if Red's curve ever restricts tiers by distance, the starting distance it checks must be Red's.
6. **The Settings fifth row on pixel.** Measured: 781 px bottom against the 756 px Back line, no horizontal overlap, inside the screen. Fixed in M8.b (749 px). It is a layout test's job to keep it that way, on both themes.
7. **Balance by rule instead of by knob.** If the escape is too easy, the temptation is to make Red move every turn. That is a different game (plan §7 recorded the choice). Tune the move limit and board size first; if the rule has to change, it changes in the GDD first.
8. **The accent comparison never ending.** M8.d has a decision at its end and the loser is deleted. Two live mechanisms is a maintenance cost the project does not want.
9. **Red's color against a red board.** The Okabe-Ito vermillion (213, 94, 0) on a red-shifted cell may not clear the contrast ratio. The character roles are palette values; if one has to move for one mode, that is a per-accent palette entry, not a special case in the renderer.
10. **Placing the scroll bar against `SCROLL_REGION`.** The module's `SCROLL_REGION` is the list's starting size. Each `TopicsState` widens its own copy to fit the widest label (right edge at 1081 on flat and 1192 on pixel, measured 2026-09-30). A bar placed against the constant would cover pixel's long labels. Place it against `self.scroll_region`, which the click routing already uses.
11. **Swipe-to-scroll on the list instead of a bar.** It feels more natural on a tablet, but the checkboxes toggle on button-down, so a swipe that starts on a row would toggle that row. Supporting a swipe means moving every checkbox toggle to button-up and adding a movement threshold to tell a tap from a drag. That changes how every checkbox click works, which is more than this problem needs. The bar leaves the list's input alone.
12. **Handling one touch twice.** SDL reports each touch twice: as `FINGER*` events in 0–1 coordinates, and as emulated mouse events in screen pixels with `event.touch` set. Handle only the mouse events, as every screen already does for taps. Adding `FINGER*` handling for the drag would move the bar twice for every finger motion.
